# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

`kagex` (origin: https://github.com/krkren/kagex) is an English-translated, SDL3/Linux-ported fork of **KAGEX** — Wamsoft's extension of the Kirikiri **KAG3** visual-novel framework (affine layers, layer level ordering, automatic actions, and the "World" environment system). It is pure script and asset content: TJS2 (`.tjs`), KAG scenario (`.ks`), CSV, and images/audio. There is **no build step and no linter**; `tools/smoketest.py` is the test (see Running).

The engine that runs it is not part of this repo. `krkrz.exe`, `SDL3.dll`, `plugin/`, and `savedata/` are all gitignored local artifacts, built from the sibling `../krkrz_dev` umbrella repo (the SDL3 variant of 吉里吉里Z; see `../krkrz_dev/CLAUDE.md`). `extrans` used to come from https://github.com/krkren/SamplePlugin; `../krkrz_dev` now builds it too. `setup.bat` and `setup.sh` were removed in commit `f6d1767` — `git show f6d1767^:setup.bat` is the reference for which build outputs get copied where (`krkrz64.exe` → `krkrz.exe`, `core/plugins/*/*.dll` + `krmovie.dll` → `plugin/`). On Linux the outputs are `build/x64-linux/core/Release/krkrz` + `_deps/sdl3-build/Release/libSDL3.so*` → repo root and `core/plugins/*/Release/lib*.so` → `plugin/`. With Arch's CMake 4 / newer GCC, configure needs `-DCMAKE_POLICY_VERSION_MINIMUM=3.5` and the full build fails inside the `krkrthreepp` plugin, so build only the targets kagex uses: `cmake --build build/x64-linux --config Release --target krkrz KAGParserEx csvParser layerExBTOA layerExImage layerExRaster scriptsEx shrinkCopy extrans krkr_richtext saveStruct getSample psdfile layerExSave AlphaMovie` (the release Linux packages ship these and more: every portable plugin krkrz_dev builds). Never modify `../krkrz_dev` or its submodules: work around engine bugs in the scripts. The 0.0.4 to 0.2.0 packages run engine 2.6.5 (`System.versionString` is `2.6.5.0`, krkrz_dev master `21d20e9` of 2026-10-20). A release package also needs `krkrz.cf` (repo root) next to the engine. On Linux `libkrkr_richtext.so` links but won't load (`undefined symbol: png_get_valid`): its link line repeats `libfreetype.a` after harfbuzz, past the png/zlib/bzip2/brotli archives. Relink it with those archives appended: take the command from `ninja -f build-Release.ninja -t commands core/plugins/krkr_richtext/Release/libkrkr_richtext.so | tail -1` (in `build/x64-linux`) and add `vcpkg_installed/x64-linux/lib/{libpng16,libz,libbz2,libbrotlidec,libbrotlicommon}.a -lm` at the end.

## Running

```bash
./krkrz.exe                   # Windows, from the repo root; project dir defaults to data/
./krkrz -datapath=savedata/   # Linux; otherwise saves go to ~/.local/share/krkren/kagex/ (krkrz.cf)
python3 tools/smoketest.py    # headless smoke test of the sample and the template (needs the engine here)
```

- `krkrz.cf` next to the engine is read as extra command-line options (one `name=value` per line, no `-`, `;` comments; `<exe name>.cf`, so `krkrz.cf` for both `krkrz` and `krkrz.exe`). It sets `orgname=krkren`/`appname=kagex`, which name the Linux/macOS save folder (`~/.local/share/<orgname>/<appname>/`); the engine's defaults are `wamsoft`/`krkrz`, shared by every game on the stock engine. `-datapath` still wins. With a `savedata*` folder next to the exe and no `-datapath`, the engine logs a "Legacy save data found" warning.
- **`tools/smoketest.py`** runs the sample (`data/`) and then `template/` as a project of its own (the template is a runnable game: `template/startup.tjs`, `system/`, `scenario/first.ks`), each with a temporary `-datapath`, and drives them through the REPL file channel (below). It plays the five demos with a clicking `Timer`, checks that the demo menu's choices measure as text (not the icon font) and that the first CG and Replay tiles are opaque, saves and loads, opens and closes the system and Extras screens, the Yes/No prompt, About and the controller buttons, then fails on an uncaught script error in the log (`Script exception raised` / `スクリプトで例外が発生しました` / `! trace :`) or a native dialog (REPL `modal`). Don't match `An exception occured at ...`: the engine logs that VM dump for **every** thrown exception, including the ones the scripts catch on purpose (plugins the SDL engine lacks, the time-of-day background fallback in `KAGEnvStage.drawLayer`). `.github/workflows/smoke.yml` runs it with `krkrz`, `libSDL3.so.0` and `plugin/` from the newest release that has `kagex_sdl3_linux_release.zip` (all releases are pre-releases, so there is no "latest"). The newest release's Linux package is a quick way to get an engine here: `gh api -H "Accept: application/octet-stream" repos/krkren/kagex/releases/assets/<id>` (from `gh api repos/krkren/kagex/releases`), then copy those three next to `data/`.

- The engine treats the first positional argument as the project directory, and looks for `startup.tjs` in it. With no argument it uses `data/` next to the exe. Engine options are `-name=value`; a bare word gets taken as the project path (a past run with a stray `usepseudo` token failed with "Cannot find storage startup.tjs").
- The feedback loop is running the game (or the smoke test) and reading the log: **`savedata/krkr.console.log`**, or the engine's stdout, which has the same lines as they happen. The file is **UTF-16LE** and appended across runs — read it with `iconv -f UTF-16LE -t UTF-8 savedata/krkr.console.log | tail -n 200`, and look for `Script exception raised` (`スクリプトで例外が発生しました` on a Japanese system) and the `! trace :` after it; an `An exception occured at <file>(<line>)` dump on its own may be an exception the scripts caught. Filenames in traces are lowercased.
- The game forces full-screen. To test without taking over the screen, run it headless: `SDL_VIDEO_DRIVER=offscreen SDL_AUDIO_DRIVER=dummy ./krkrz -datapath=savedata/ -replfile=<dir>`, and drive it through the engine's REPL file channel (`../krkrz_dev/src/core/doc/REPL.md`: write TJS to `<dir>/cmd.tmp`, rename to `cmd`, read and delete `<dir>/resp`). REPL commands are evaluated as one expression: wrap statements in `(function() { ...; return x; })()`, or only the first one runs; TJS has no closures (an inner function can't see the outer locals) and no `finally`. Injected keys don't change `System.getKeyState`, and KAG checks Return/Space with `getKeyState` (`checkProceedingKey`), so a `keyDown`+`keyUp` in one command does nothing: press with `keyDown`, wait a frame, then `keyUp` (the smoke test's `key()`), or click with `Agent.click`. Holding a key (Ctrl, R2) can't be simulated. Under the offscreen driver `Agent.captureScreen` returns black with the default GL draw device, so render `kag.primaryLayer` into a new Layer with `piledCopy` and `saveLayerImage(path, "bmp")` (that BMP's header says the pixels start at byte 56, but they start at 54; BGRA, bottom-up). `piledCopy` reads the layer buffers, so it hides anything that never reached the screen (a missing `update()`). To see the real frame, add `-drawdevice=sdl`, then `kag.setZoom(1, 1), kag.setInnerSize(1920, 1080)` and `Agent.captureScreen(path)` (a PNG written on the next frame). `Agent.click` takes window coordinates: the offscreen window is 1024x768 with the 1920x1080 game letterboxed into it.
- `savedata/*.ksd` persists system/scenario variables (`sf.*`, `scflags`) between runs, including things like the saved full-screen preference. When a config change appears to have no effect, stale savedata is a likely cause.

## Layout and load order

- `template/` — the reusable KAGEX framework. `template/system/*.tjs` is the whole runtime (~60 files); the other `template/*` folders are empty placeholders for a new game.
- `data/` — the sample game. In this repository it has no `system/` of its own: `data/startup.tjs` runs `data/system/Initialize.tjs` when there is one, and otherwise adds `../template/system/` to the auto path and executes `../template/system/Initialize.tjs`. The platform builds copy `template/system` into the package as `data/system` (a browser or phone build has nothing outside `data/`); the zip packages keep `template/` next to `data/`. Shipping a real game means copying `template/system` + `template/startup.tjs` into `data/`.
- `doc/` — the KAGEX reference, in English: `kagex.txt` (new/changed tags vs. stock KAG3), `action.txt` (action system), `world.txt` / `world_inst.txt` / `world_use.txt` (World extension: `envinit.tjs` schema, character/stage/time tags). Read these before changing tag behavior; stock KAG3 knowledge alone is not enough.

`template/system/Initialize.tjs` drives everything, in this order:

1. Registers auto paths: `data/` then a fixed list of subfolders (`video, others, rule, sound, bgm, fgimage, bgimage, scenario, image, system, voice, face, init, sysscn, main, evimage, thum, uipsd`), each also accepted as a `<name>.xp3` archive. **Later-registered paths win**, so anything under `data/*` shadows the same filename in `template/system/`. Storage lookup is by bare filename across all auto paths — filenames must be globally unique unless shadowing is intended.
2. Runs `Storages.tjs` (`data/main/Storages.tjs`) — add nested asset folders there via `setupSubFolders([...])`; a new top-level folder outside the fixed list is not searched.
3. Links plugins (see below), then loads `AppConfig.tjs` (optional) and `Config.tjs`.
4. Loads the system classes, then `Override.tjs`, creates the `kag` window, attaches `KAGWorldPlugin` (`world.tjs` + `KAGEnv*.tjs`, configured by `envinit.tjs`), runs `AfterInit.tjs`, and finally `kag.process("first.ks")`.

In the sample, the game-side hooks all live in `data/main/`: `Config.tjs`, `Override.tjs` (class/function overrides, loads `MyHistoryLayer.tjs`), `AfterInit.tjs` (key bindings etc.), `envinit.tjs` (World definitions: times, stages, characters, poses), `first.ks` → `logo.ks` → `title.ks`, the system-menu scenarios (`config.ks`, `save.ks`, `load.ks`, `cgmode.ks`, `musicmode.ks`, `replay.ks`) and their CSV lists. Story/demo scripts are in `data/scenario/` (`s0001.ks` is the demo menu). Prefer these hooks over editing `template/system/` when a change is game-specific.

## Platform builds

The Windows and Linux zips come from the release workflow, which builds krkrz_dev itself. The other packages come from Wamsoft's platform kits, which build krkrz_dev without changing it, from configs at the repository root: `linux-config.json` (krkrz_linux: a Linux folder built in Valve's Steam Linux Runtime 3.0 "sniper" container), `web-config.json` (krkrz_web), `app-config.json` (krkrz_android) and `ios-config.json` (krkrz_ios), with this repository as `PROJECT_DIR` and `KRKRZ_BASE` the folder that holds `krkrz_dev` and the kit. macOS uses krkrz_dev's own `arm64-osx` preset. `.github/workflows/platforms.yml` builds and smoke-tests all five, with the engine (`21d20e9`, as for the zips) and the kits pinned in its `env`. It runs on pushes to `platforms/**` branches (`[platforms: linux web]` in the commit message builds only those, `[platforms: none]` nothing) and from the release workflow (`workflow_call` with the release commit as `ref`). Each job uploads its build before the smoke test (`kagex-linux`, `kagex-web`, `kagex-android` (release) and `kagex-android-debug`, `kagex-ios-simulator`, `kagex-macos`) and force-pushes its logs, screenshots and an `<log>.errors` digest of each log to branch `ci/platform-results-<job>`; job logs themselves can't be read from this environment. `.github/workflows/pages.yml` puts a release's `kagex_sdl3_web.zip` on GitHub Pages (the release workflow starts it). The packages hold `data/` with `template/system` copied in as `data/system`, which `data/startup.tjs` prefers.

- **Plugin order.** List a krkrz_dev plugin first in a config's `plugins`: tp_stub's `krkrz.cmake` caches `NCBIND_DIR` relative to the first plugin folder that includes it, and with the kit's `virtualpad` first that was the kit's folder, which has no ncbind.
- **Linux.** `cmake.options` sets `CMAKE_CXX_STANDARD_LIBRARIES` to freetype's archives (png, zlib, bzip2, brotli) so they end every C++ link: the same krkr_richtext fix as the relink above. The smoke test runs the package on the runner itself, with Mesa's EGL installed.
- **Web.** krkr_richtext doesn't compile for wasm32 at engine 2.6.5 (its `main.cpp` casts a `tTJSVariant` to `tjs_intptr_t`, which tp_stub only converts to on Apple or where `intptr_t` is `int64_t`), so the web build draws text with `drawText`. `.github/platforms/web-plugins.py` edits krkrz_web's built-in plugin list in the CI checkout, dropping the plugins from Wamsoft's private repositories. The site downloads files on demand (`web://`), and the save folder (`user://`) is SDL storage rather than local files (see the bookmark notes under the BMP bug). `lowercase` puts the files in lower case for case-sensitive hosts such as GitHub Pages, and `coi-serviceworker.js` supplies the COOP/COEP headers there. `.github/platforms/web-static-host.py` readies the site for a static host, in the staging step and again in `pages.yml` (0.2.0's zip lacks both changes): the engine reads the `web://` file list from `gamedata/krkrz_files.json`, which the kit writes to `gamedata.krkrz_files.json` and only its `serve.py` answers with, so it copies the file there (without it Pages stopped at `Config.tjs not found`); and coi-serviceworker reloads the page on `updatefound`, before its worker is active, so on Pages the reloaded page was sometimes left uncontrolled and not `crossOriginIsolated` (`SharedArrayBuffer transfer requires self.crossOriginIsolated`, nothing starts until the visitor reloads), so it sets `window.coi.doReload` to wait for `navigator.serviceWorker.ready`. The web smoke test serves the site with `python3 -m http.server`, as Pages does, rather than `serve.py`, and `pages.yml` runs it on the live site after each deploy (`ci/platform-results-pages`). Headless Chromium lets the page go full screen without a click, and the full-screen canvas covers the loading screen, so a first visit screenshots black there; a real browser refuses that and shows "Click / tap to start" (add an init script that rejects `requestFullscreen` to see it). The build has no `Agent` class: the smoke test posts keys with `kag.postInputEvent` and runs every command from a `Timer`, because a scenario load started inside a `krkrz_repl_eval` call crashed the page.
- **Android.** The kit asks Gradle for the SDK's CMake 3.22.1, but with krkr_richtext the engine downloads ICU with an option CMake 3.24 added (`DOWNLOAD_EXTRACT_TIMESTAMP`): CI installs the newest SDK CMake 3.x and changes `version` in the kit's `app/build.gradle`. There's no `a11y` plugin: it turns on `KRKRZ_USE_A11Y`, and at engine 2.6.5 the engine's AccessKit setup can't find its Android library (`find_library` in the NDK cross-compile), so `libkrkrz.so` didn't link. The x86_64 libvpx (for the emulator) needs `nasm`. The smoke test drives the debug build through its REPL socket (`<applicationId>.repl`, forwarded with adb); the package is the kit's `release-debug` build (optimized, signed with the debug key).
- **iOS.** A Simulator build (a device build needs an Apple Developer team), Debug, without krkr_richtext (with it, CMake's Xcode generator stops with "duplicate object ids not allowed"; a bisect pinned it to that plugin) and with `a11y` off. krkrz_ios builds only the browser REPL (`-replweb`), which the smoke test drives through `POST /pad/exec`. Screenshots of the Simulator come out black on the CI runners, even through `Agent.captureScreen`, so there the smoke test checks the game's state only.
- **macOS.** The macOS runners' CMake 4 needs `CMAKE_POLICY_VERSION_MINIMUM=3.5` (set for every job). The job renames the app to `KAGEX.app`, copies the game into `Contents/Resources/data`, sets the name, bundle id, version and icon, and signs it ad hoc again: adding the files broke the build's own signature, which macOS reports as a damaged app. Its smoke test runs with SDL's cocoa driver; the offscreen one has no OpenGL ES there.
- **Smoke test on the platforms.** `--target android|ios-sim|web` runs the sample's steps; clicks go through `kag.onPrimaryClick` because `Agent.click` takes window coordinates, which differ on every platform. A save failure leaves the save-failed message open, which then swallows Return, the arrows and the pad buttons in later steps.

## Conventions and gotchas

- **Two `Config.tjs` files.** `data/main/Config.tjs` is the one in effect (it shadows `template/system/Config.tjs`). Recent commits keep both in sync for settings like `scWidth`/`scHeight` (currently 1920x1080); do the same. Setting lines use the `;name = value;` form, and the `//[start-...-additionals]` / `//[end-...]` markers must stay — `UpdateConfig.tjs` parses both when migrating configs. The `KAGWindow_config` etc. functions run `incontextof` the target object, so settings like `scWidth` become **members of `kag`**, not globals.
- **Plugin linking.** Plugins are linked by explicit relative path with a `.dll` name on every platform — `Plugins.link("plugin/foo.dll")` — wrapped in `try {} catch {}` and, where possible, guarded by a `typeof` check on a symbol the plugin provides (avoids double-loading on case-sensitive Linux, and tolerates plugins the SDL3 build provides natively or lacks). `Initialize.tjs` does this through `KAGLinkPlugin(name)`, which logs a failure to the console instead of swallowing it. Follow this pattern; bare `Plugins.link("foo.dll")` was deliberately removed in `0710553` (the x64 Windows engine's own plugin folder is `plugin64/`). On non-Windows engines (`System.platformTag` present and not `"windows"`), the top of `Initialize.tjs` wraps `Plugins.link` to drop the `plugin/` prefix, because the SDL engine turns `plugin/Foo.dll` into `libplugin/Foo.so`; its own search already finds `plugin/libFoo.so`.
- **Linux compatibility.** Storage names in scripts must match file case exactly, and use `/` separators. Plugin names too: the packages ship `libsaveStruct.so`, so `Plugins.link("plugin/savestruct.dll")` only worked on Windows. That includes data files such as `musiclist.csv` (it listed `BGM01` for `bgm01.ogg`, which played on Windows only).
- **SDL3 port patches.** The end of `Initialize.tjs` re-applies the window size with `kag.setZoom(kag.zoomNumer, kag.zoomDenom)` unless full-screen, so a windowed start keeps the zoom the constructor picked for a display smaller than 1920x1080 (it used to force `setInnerSize(scWidth, scHeight)`). Both `Config.tjs` files shadow `getInitialFullScreenState`: full-screen on the first launch, then the saved `scflags.fullScreen`. The SDL engine switches full screen asynchronously, so `kag.fullScreen` (which reads the window back) still reports the old mode right after a switch: `changeFullScreenOrWindow` records the requested mode in `kag.fullScreened`, and anything deciding by the current mode (the Config screen's buttons, the size at the end of `Initialize.tjs`, the saved preference) should read `fullScreened`. Be careful reordering anything around window creation and `kag.process("first.ks")`. The SDL engine's `Window` has no `menu`: `KAGWindow_createMenus` (`Menus.tjs`, and the sample's copy in `Override.tjs`) builds the menu items on the stand-in `Menu` class `Menus.tjs` defines, and the framework's version marks that with `kag.menuBarStandIn`; without it a game made from the template stopped at start-up (`Member "menu" does not exist`). The Debug menu is unreachable there, so KAG's debug mode (`debugWindowEnabled`: on unless `-debugwin=no`, which a release should set) gets Shift+F12 (debug window) and Shift+F11 (debug level) in `processKeys`. The sample's `KAGWindow_createMenus` copy sets `menuBarStandIn` too. The SDL engine has no `Pad` class either: `initLogPad` returns early and `UpdateConfig.tjs` writes `Config.tjs.merged` instead of showing a Pad. `MainWindow.tjs` only takes its windowEx path (extended events, menu-bar hiding, registry cursors) when both `registerExEvent` and `exSystemMenu` exist. Newer engines build `registerExEvent` in on every platform, while `exSystemMenu` only comes from the windowEx plugin. Likewise `Window.minimize` is built in, but the `MenuItem.bi*` icons are windowEx's, so `SetWindowControlMenu` (`Menus.tjs`) returns early without them; it used to throw `Member "biMinimize" does not exist` on every switch between full screen and a window, which skipped the rest of the `fullScreen` setter (the `afterChangeScreenMode` hook, the menu-bar update).
- **File encoding.** Most scripts are UTF-8 **with BOM**, but not all (e.g. `template/system/Config.tjs` has none); line endings and a doubled-blank-line artifact (left over from a CRLF conversion) vary by file. Preserve whatever the file already uses and keep diffs minimal — do not normalize whitespace, strip BOMs, or collapse the blank lines as a drive-by. `◆`/`●` markers and some Japanese comments are intentional.
- **The sample's images are generated** by `tools/assets/` (README there): `make_ui.py` draws everything in `data/image` plus `template/system/LineBreak*`/`PageBreak*`, `fgimage/star.png` and `thum_replay_char` in one theme (the Yes/No dialog's: lavender panel (166,144,255), violet (80,37,255) borders and hard shadows, white buttons that go violet when hovered or selected, white labels with a navy (1,0,98) outline, light dotted screen backgrounds), with labels from the Noto Sans CJK JP subsets in `tools/assets/fonts`. `upscale.py` rebuilds `fgimage/ch_*`, `bg01_01`, `event1` and `thum_event1` from the original art in `tools/assets/src` with Real-ESRGAN in NumPy (anime model for sprites, x4plus for the photos; 4x, then down to 1.8x, or 2.4x and the middle 1080 lines). Change the scripts and rerun them instead of editing the PNGs; `title.png` and `thum_replay_char` are drawn from the upscaled `bg01_01` and `ch_0_0_1`, so run `upscale.py` first. A panel's hard shadow (`Canvas.panel`) is drawn only outside the panel, so translucent panels (the message window, the choices) stay evenly see-through; anything drawn inside a rounded panel has to stay inside its border's rounded inner edge (the message window's top highlight is clipped to it).
- UI coordinates in `.ks` files (`title.ks`, `config.ks`, …) and the images in `data/image/` are authored for a specific resolution; a resolution change means touching both. The screens share a grid: content from x 290 to 1630, a header title at 290 with a rule at y 170, and 180x64 nav buttons (`return`, the Extras tabs, `config_title`/`config_initial`) right-aligned at y 78. `title.ks`/`title.png`, `config.ks` (with its `config_*` and `slidebar*` images) and the extras screens `cgmode.ks`/`replay.ks`/`musicmode.ks` (`*mode_base`, `extra_*`, `cgmode_page*`, `cgmode_thum_*`, `musicmode_*`, `track*`) and `save.ks`/`load.ks` (`save_base`/`load_base` (semi-transparent so the scene shows through), `sl_win_base`, `*_win_over`, `page1-9`, `newdata`; save thumbnails are 234 wide via `thumbnailWidth` in `data/main/Config.tjs`, and `fileDataButton` in `Override.tjs` lays out the slot: it draws the thumbnail, badge and text into each of the button's three states, so `sl_win_base` is the normal look and `save_win_over`/`load_win_over` the hovered one) are at 1920x1080, as is the choice menu that opens on START (`[selopt]` in `first.ks` sets its area and `size=36`; bars are `select_normal`/`select_over`, and `SelectLayer` spaces the choices evenly within the area). The demo scenes are 1920x1080 too:
  - Art: `bg01_01` and `event1` are 2.4x the 800x600 originals, trimmed to 16:9; character sprites (`fgimage/ch_*`) are 1.8x (`upscale.py`). `black`/`white` are 1920x1080. The `LineBreak`/`PageBreak` glyphs are 43px cells, 16 frames that the `.asd` plays forwards and back. `test.webm` is 1.8x (2880x1080, side-by-side alpha).
  - Message window: `[initscene]` in `macro.ks` sets it to 1800x330 (12px of that is the shadow), with the `msg_*` buttons (124x42) right-aligned inside its top edge and the name in `namebox` (`nameframe`, a framework attribute of `[position]`: `NameLayer` loads it behind the text) straddling the top edge. The name has no brackets: the sample's `dispNameFilter` is gone, and `MyHistoryLayer.storeName` brackets it in the history. The sample `Config.tjs` text is 39 (line spacing 5, ruby 15/-3).
  - World (`envinit.tjs`): `yoffset` and vertical motion are x1.8. Horizontal positions and moves are x2.4, so `posleft`/`outleft` etc. sit at the same fractions of the wider screen.
  - Hardcoded scenario offsets (`layer.ks` character/rotation origin, `char.ks` walk-off, `envlayer.ks` star paths) were scaled the same way.
  - History log (`MyHistoryLayer.tjs`): full-screen `log_base` (which draws the scroll bar's track), controls placed for 1920 wide, text 36/42. Its margins come from the `historylayer-additionals` in `data/main/Config.tjs`, which override the class defaults: `marginR = 176` keeps lines clear of the page buttons at x 1766.
  - Yes/No prompts (`template/system/YesNoDialogLayer.tjs`, which `YesNoDialog.tjs` loads; the framework's since 0.0.5, so games made from the template get them too), designed at 1920x1080 (the old box's lavender and purple, square with 14px corners and a hard offset shadow): every `askYesNo` uses `dialog_base` (760x300 panel) or, for a message longer than two lines, `dialog_wide_base` (1080x400). The images hold no text: the message (shortened through `yesnoMap`, or as given) is word-wrapped and drawn bold in white with a navy outline, and the `dialog_button_normal/over` shapes get their "Yes"/"No" labels drawn into each button state (`drawYesNoLabel`), all with `kag.chDefaultFace` through krkr_richtext when the message window uses it. So no prompt reaches the stock `YesNoDialogWindow` (it's `askYesNoWindow` now, used only before the game window exists). The images are in `template/system/` (a game can shadow them from `data/image`). `yesnoFrames` holds each frame's text area and button row. `YesNoDialogLayer` overrides `close()`: closing it without an answer runs the No path, because Esc (`DialogLayer.onKeyDown`), a right-click on the panel or a button (`DialogLayer`/`DialogButtonLayer.onMouseUp`) and outside it (`rightClickHook`) all just call `close()`, which skipped `noFunc`/`doneFunc`; `answered` keeps it to one answer. The focus starts on No. Before the game window exists, `askYesNo` uses `System.confirm` (the SDL engine can't `showModal` a window when it's the only one).
  - About (F1): `showAbout()` (`YesNoDialogLayer.tjs`, loaded on demand through a property in `Initialize.tjs`) shows `AboutDialogLayer`, the Yes/No frame with the title, version and copyright from `sf.software_*` (set in `first.ks`; without a title, `System.title`), the engine version (`System.versionString`) and a Close button; it picks the wide frame when the lines don't fit. `KAGWindow.onHelpAboutMenuItemClick` calls it unless `aboutInWindow` is false. The old About opened a second, modal `KAGWindow` running `about.ks`, and pressing F1 crashed the game on Linux; `about.ks` and `aboutWidth`/`aboutHeight` are only for `aboutInWindow = false`. - **Alpha movies in layers** (`[image movie=... alpha=1|2]`) go through `GFX_Movie.tjs`, which copies each frame with `assignImages`. - **English text in scenarios.** In normal mode (`[linemode]` with no mode, `ignoreCR` on), a new line in the `.ks` adds nothing, so text split by tags (`[wact]`, `[emb]`, …) runs together. End such segments with punctuation and a trailing space (trailing spaces are kept). Plain text lines get word wrap from this fork's `needsToBeWrapped()` in `MainWindow.tjs`, which breaks before a word that won't fit. The space at the break is dropped through `wrapDropSpace`/`wrapDropSpaceHist`, which the `ch` handler checks; assigning `text = ""` inside that function had no effect. Its state belongs to one scenario line, keyed by `conductor.curStorage:curLine` (not by content, so identical lines in a row each wrap), and `internalRestoreFlags` resets it. The `ch` handler calls it after its early returns, because a handler that returns -3 or -5 gets the same tag run again (`Conductor.waitAndBreak` re-queues it): a page break the wrap returns sets `wrapResume`, and the re-run measures from the new page and drops the space instead of counting it as another word. The `wrapNewPage` flag that did this before was never cleared, so after one wrap overflowed a page every later wrap became a page break. Lines it skips (any line containing `[r]`, or starting with a tag or tab) fall back to KAG's character wrap, which can split words. There, `MessageLayer.processCh` and the history layers drop a space that would start a wrapped line. Break long English lines yourself with `[r]` at a sentence boundary when they contain tags. `[initscene]` uses `[linemode mode=page]`, where every scenario line stands alone.
- **【name】 tags must use the character's key** from `envinit.tjs` (the same name as its tag, e.g. `【ai】` for `[ai ...]`). Keys are case-sensitive. Voices set with `[ai voice=N]` are looked up by that key, and so are faces and the character link. The translation had written `【Ai】`, which silently dropped the voice. The displayed name comes from the character's `nameAlias` ("Ai"), or from `【ai/Display】` for one line.
- **Never test a string as a boolean** (`if (s)`, `s ? a : b`). The current engine converts it to a number, so `"event1"` is false, and an empty string segfaults it (`tTJSVariantString::ToInteger`). Compare instead: `if (s != "")`. This crashed the Replay screen whenever an unlocked entry had no thumbnail.
- **Font faces on the SDL engine.** A face name the engine has not registered (e.g. `MS Gothic` on Linux, and on some machines plain `Noto Sans CJK JP` when only the Light weight is registered) is drawn with its `elements_basic` icon font, so text shows as `←←←`. The engine's own default face (an empty face) has the same problem here. So `userFace` and the history `fontName` in both `Config.tjs` files, plus the explicit faces in `about.ks`, `Override.tjs` and the history classes' defaults, are face lists with Yu Gothic first: `"Yu Gothic Medium,Yu Gothic,Noto Sans JP,Roboto"` (the template uses the same list). **Noto Sans JP ships in `template/system/notosansjp-regular.otf`** (the engine's own `resource/notosansjp-regular.otf`, SIL OFL, `notosansjp-OFL.txt`): since engine 2.5.0 the engine embeds only Roboto, so Japanese depended on system fonts and drew as U+FFFD boxes without them. `Initialize.tjs` registers it with `Font.registerFontFile(path, "Noto Sans JP")` after the plugins, which records the name without opening the file; `Font.getVarAxes` then resolves it and krkr_richtext draws it. Where the engine already has a font of that name (the browser build bundles Noto Sans JP in its `resource/`), it loads the file with `Font.addFont` instead: the engine finds a bundled font only in the exact style asked for, and its rasterizer keeps one face chain, rebuilt only when the first face of the list changes, so the first text drawn in a face list being bold (the `[select]` choices) left that chain on the icon font (`elements_basic`, which its fallback means to skip): every text came out as arrows measuring 0 wide. A loaded font is found in any style. To check rendering without system fonts, run with `FONTCONFIG_FILE` pointing at a config whose only `<dir>` is empty. Up to 0.0.4 the list was `"Yu Gothic Medium,Yu Gothic,MS Gothic,Noto Sans CJK JP,Noto Sans CJK JP DemiLight,Noto Sans CJK JP Light,Roboto"`, which is now in `previousDefaultFaces`; the notes below about system Noto CJK names explain why that list looked like that. Unknown names in a list are skipped, and both the engine and krkr_richtext pick a font per character from the list. Yu Gothic leads on Windows because its Latin letters are proportional and kerned: MS Gothic's are fixed-width, which made English look gappy (`over lap`) and left krkr_richtext nothing to kern. Yu Gothic Medium is the readable weight on screen; plain Yu Gothic is the fallback where Medium is missing. Don't pick a font that isn't the first in its `.ttc` (MS PGothic, MS UI Gothic, Yu Gothic UI, MS PMincho): the engine's `drawText` gets those right, but krkr_richtext draws the collection's first font instead (MS Gothic, Yu Gothic, MS Mincho), so MS PGothic comes out monospaced again. That's an upstream bug (plugin or engine), seen on Windows; the template used `MS PMincho` until 0.0.4 and was affected. Plain `Noto Sans CJK JP` fails on Arch because the Light file also claims the Regular style, while the weight-suffixed names resolve. Roboto ships with the engine, so it is always available for Latin text. `kag.chDefaultFace` is saved into the system variables (`*sc.ksd`, `scflags`) and wins over `Config.tjs`. When a saved value is a single old-style name (e.g. `MS Gothic`), the restore code in `MainWindow.tjs` keeps it first and appends the configured list. A saved value equal to a default some earlier release shipped (`previousDefaultFaces` in `MainWindow.tjs`, which now lists `ＭＳ ゴシック`, `MS Gothic`, the 0.0.2 list and the template's old values) is replaced by the configured default instead, so a changed default reaches existing saves; add the old value there whenever a default changes. Without `-datapath` the engine keeps that data in `~/.local/share/wamsoft/krkrz/`, not `savedata/`. Use the face lists for any new text too.
- **krkr_richtext.** With `useRichText` (MessageLayer_config, on in both `Config.tjs` files) and the plugin loaded, `drawTextToLayer` in `MessageLayer.tjs` draws message text, ruby and the name box through `RichTextFontApp`: vector edges/shadows built from the layer's edge/shadow settings, fake bold, and in `processCh` kerned advances (the exact width of the line's run, rounded per character). Vertical text and bitmap fonts keep the normal path, as does anything when the plugin or the fonts are missing. The `[select]` choices and the history log (both `data/main/MyHistoryLayer.tjs` and `template/system/HistoryLayer.tjs`) follow the message layers' `useRichText` with `RichTextFontApp` instances of their own: `SelectLayer` puts its app into the style dictionary as `richTextApp`, and the history draws whole lines through `drawHistoryText` (no edge or shadow, as before). `SelectLayer` borrows `MessageLayer.drawTextToLayer` `incontextof` that style dictionary, so that function may only touch members the dictionary has (a call to a MessageLayer method there broke every `[select]`). Text widths must come from the path that draws the text, or English lines break in the middle of a word once the font is proportional: `MessageLayer.measureText`, `SelectLayer.measureText` (choice centering) and `HistoryLayer.textWidth` (wrapping, action marks, indent) measure with krkr_richtext when it draws, and the word wrap in `MainWindow.tjs` (`needsToBeWrapped`) measures words through `msgTextWidth`/`histTextWidth`. Edges and shadows: `Layer.drawText` draws both as a blurred copy of the glyphs. The edge becomes a stroke reaching `edgeExtent` past the glyphs, fully opaque from `edgeEmphasis` 255 up (the default 512) and fainter below; a shadow with `shadowWidth` (blur) > 0 gets three widening translucent strokes around the offset copy. The sample's settings (shadow, offset 2, no blur) render the same either way. The baseline comes from the engine's `getGlyphDrawRect("H")`, so lines sit where `drawText` put them. The line layer only reaches `lineLayerPadding` (4) below the text cell, and krkr_richtext's descenders (g, y) plus the shadow reach further, so they were cut off at the bottom of each line: `MessageLayer.updateLineLayerPadding` (from `initLineLayer`) widens the padding per line from `RichTextFontApp.bottomOverhang`; it's symmetric and every offset uses it, so nothing moves. `drawTextEx` only calls `update()` on the glyphs' ink box, which leaves shadows and edges off the screen until something else repaints there (text looked clipped while typing, then changed when the line was committed), so `RichTextFontApp.drawText` updates the whole padded cell itself. **Never pass `RichText.registerFont` (or `Font.getFontInfo`/`Font.queryFonts`) a face name the engine can't resolve:** the engine then opens every system font to search their names, and its pooled file allocator deadlocks (it runs the storage-cache pressure callback while holding its own mutex, at 75% of `-filepoolsize`, default 256 MB). A hung engine ignores SIGTERM; use `kill -9`. `RichTextFontApp.getFonts` only registers names that `Font.getVarAxes` resolves (it uses the same lookup as `drawText`, without the search) and that the engine actually draws; plain `Noto Sans CJK JP` passes the first test on Arch but draws nothing, so the chain here is DemiLight → Light → Roboto.
- **Engine BMP bug.** The current engine's BMP writer puts `bfOffBits = 56` in the header but writes the pixels at byte 54, and its reader trusts the header. The cause is in the engine's `common/visual/GraphicsLoaderIntf.h`: `#pragma pack(push, 1)` around `TVP_WIN_BITMAPFILEHEADER` is only applied under `_WIN32`, so on Linux (and macOS) the 14-byte header struct is padded to 16 and `sizeof` gives 56; Windows builds write correct BMPs. Don't patch the engine (krkrz_dev is off-limits). So anything saved with `saveLayerImage(..., "bmp")` comes back color-shifted. This is a krkrz bug. To avoid it, bookmarks (`MainWindow.tjs`) now save their thumbnail as PNG: the save files are `dataN.png`, the save data starts at `calcThumbnailSize().size` (sized for an uncompressed RGBA PNG), and the thumbnail is forced opaque because PNG keeps the snapshot's meaningless alpha. `thumbnailDepth` is unused, and old `.bmp` saves are no longer picked up (only 0.0.1, the 800x600 Windows package, wrote them: PNG thumbnails came in 0.0.2). The engine picks image decoders by file extension, so PNG data in a `.bmp`-named file won't load. The PNG is shorter than that offset, and seeking past the end of a file fails on some storage ("Seek error" in the browser), so `saveThumbnailAndData` (used by `saveBookMarkToFile` and `rewriteBookMarkToFile`) grows the file to the offset with `Storages.truncateFile` first. Where the save folder isn't a local file (`user://` in the browser, Android and iOS builds), `truncateFile` throws "Cannot get local name": the file is then put together in `Storages.getTemporaryName()` (a native path, made a storage name by `localStorageName`) and copied over with `Storages.copyFile`. Before this, every save there failed and showed the save-failed message, which blocked the title screen's anchor save.
