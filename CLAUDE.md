# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

`kagex` (origin: https://github.com/krkren/kagex) is an English-translated, SDL3/Linux-ported fork of **KAGEX** — Wamsoft's extension of the Kirikiri **KAG3** visual-novel framework (affine layers, layer level ordering, automatic actions, and the "World" environment system). It is pure script and asset content: TJS2 (`.tjs`), KAG scenario (`.ks`), CSV, and images/audio. There is **no build step and no linter**; `tools/smoketest.py` is the test (see Running).

The engine that runs it is not part of this repo. `krkrz.exe`, `SDL3.dll`, `plugin/`, and `savedata/` are all gitignored local artifacts, built from the sibling `../krkrz_dev` umbrella repo (the SDL3 variant of 吉里吉里Z; see `../krkrz_dev/CLAUDE.md`). `extrans` used to come from https://github.com/krkren/SamplePlugin; `../krkrz_dev` now builds it too. `setup.bat` and `setup.sh` were removed in commit `f6d1767` — `git show f6d1767^:setup.bat` is the reference for which build outputs get copied where (`krkrz64.exe` → `krkrz.exe`, `core/plugins/*/*.dll` + `krmovie.dll` → `plugin/`). On Linux the outputs are `build/x64-linux/core/Release/krkrz` + `_deps/sdl3-build/Release/libSDL3.so*` → repo root and `core/plugins/*/Release/lib*.so` → `plugin/`. With Arch's CMake 4 / newer GCC, configure needs `-DCMAKE_POLICY_VERSION_MINIMUM=3.5` and the full build fails inside the `krkrthreepp` plugin, so build only the targets kagex uses: `cmake --build build/x64-linux --config Release --target krkrz KAGParserEx csvParser layerExBTOA layerExImage layerExRaster scriptsEx shrinkCopy extrans krkr_richtext saveStruct getSample psdfile layerExSave AlphaMovie` (the release Linux packages ship these and more: every portable plugin krkrz_dev builds). Never modify `../krkrz_dev` or its submodules: work around engine bugs in the scripts, and list the ones that can't be worked around in `UPSTREAM.md` (what they cost and what would fix them upstream, most important first). The 0.0.4 to 0.12.1 packages run engine 2.6.5 (`System.versionString` is `2.6.5.0`, krkrz_dev master `21d20e9` of 2026-10-20). A release package also needs `krkrz.cf` (repo root) next to the engine. On Linux `libkrkr_richtext.so` links but won't load (`undefined symbol: png_get_valid`): its link line repeats `libfreetype.a` after harfbuzz, past the png/zlib/bzip2/brotli archives. Relink it with those archives appended: take the command from `ninja -f build-Release.ninja -t commands core/plugins/krkr_richtext/Release/libkrkr_richtext.so | tail -1` (in `build/x64-linux`) and add `vcpkg_installed/x64-linux/lib/{libpng16,libz,libbz2,libbrotlidec,libbrotlicommon}.a -lm` before its trailing ` && :` (the command is `: && c++ ... && :`, so archives added after that go to the no-op `:` and the relink changes nothing; check with `nm -D` that no `png_` symbol is left undefined).

## Running

```bash
./krkrz.exe                   # Windows, from the repo root; project dir defaults to data/
./krkrz -datapath=savedata/   # Linux; otherwise saves go to ~/.local/share/krkren/kagex/ (krkrz.cf)
python3 tools/smoketest.py    # headless smoke test of the sample and the template (needs the engine here)
```

- `krkrz.cf` next to the engine is read as extra command-line options (one `name=value` per line, no `-`, `;` comments; `<exe name>.cf`, so `krkrz.cf` for both `krkrz` and `krkrz.exe`). It sets `orgname=krkren`/`appname=kagex`, which name the Linux/macOS save folder (`~/.local/share/<orgname>/<appname>/`); the engine's defaults are `wamsoft`/`krkrz`, shared by every game on the stock engine. `-datapath` still wins. With a `savedata*` folder next to the exe and no `-datapath`, the engine logs a "Legacy save data found" warning.
- **`tools/smoketest.py`** (`--packaged --engine <exe>`: a desktop package of the sample, run without a project folder, sample steps only) runs the sample (`data/`) and then `template/` as a project of its own (the template is a runnable game: `template/startup.tjs`, `system/`, `scenario/first.ks`), each with a temporary `-datapath`, and drives them through the REPL file channel (below). It compiles the scripts in `!scnlist.txt` (`KAGCompileScenarios`), plays the seven demos with a clicking `Timer` (compiled, where the data folder is writable), saves and loads in the middle of compiled `char.ks`, checks the animated character's blinking and lip-sync and the Live2D character's, and the Live2D model on a KAG and a World layer (with a stand-in for the plugin where it isn't there), that the demo menu's choices measure as text (not the icon font) and that the first CG and Replay tiles are opaque, saves and loads, opens and closes the system and Extras screens, the Yes/No prompt, About and the controller buttons, checks the line breaking on a message layer of its own (`WRAP_TJS`) and positional sound, and on the desktop the menu bar (switched to a window: the window's size, F10, a click on Help's title, Help > Controls, no bar in full screen), the controls list, F12's screenshot and, through `Agent.a11yTree`/`a11yAction`, what a screen reader gets (the Yes/No prompt's buttons, the demo menu's choices, a picked demo's first text), switches the title, a line of `char.ks`, the demo menu and Config to Japanese and back (it puts the sample in English first), then fails on an uncaught script error in the log; on the desktop it also runs `-scncompile=all` in an engine of its own (`Script exception raised` / `スクリプトで例外が発生しました` / `! trace :`) or a native dialog (REPL `modal`). Don't match `An exception occured at ...`: the engine logs that VM dump for **every** thrown exception, including the ones the scripts catch on purpose (plugins the SDL engine lacks, the time-of-day background fallback in `KAGEnvStage.drawLayer`). `.github/workflows/smoke.yml` runs it with `krkrz`, `libSDL3.so.0` and `plugin/` from the newest release that has `kagex_sdl3_linux_release.zip` (all releases are pre-releases, so there is no "latest"). The newest release's Linux package is a quick way to get an engine here: `gh api -H "Accept: application/octet-stream" repos/krkren/kagex/releases/assets/<id>` (from `gh api repos/krkren/kagex/releases`), then copy those three next to `data/`.

- The engine treats the first positional argument as the project directory, and looks for `startup.tjs` in it. With no argument it uses `data/` next to the exe. Engine options are `-name=value`; a bare word gets taken as the project path (a past run with a stray `usepseudo` token failed with "Cannot find storage startup.tjs").
- The feedback loop is running the game (or the smoke test) and reading the log: **`savedata/krkr.console.log`**, or the engine's stdout, which has the same lines as they happen. The file is **UTF-16LE** and appended across runs — read it with `iconv -f UTF-16LE -t UTF-8 savedata/krkr.console.log | tail -n 200`, and look for `Script exception raised` (`スクリプトで例外が発生しました` on a Japanese system) and the `! trace :` after it; an `An exception occured at <file>(<line>)` dump on its own may be an exception the scripts caught. Filenames in traces are lowercased.
- The game forces full-screen. To test without taking over the screen, run it headless: `SDL_VIDEO_DRIVER=offscreen SDL_AUDIO_DRIVER=dummy ./krkrz -datapath=savedata/ -replfile=<dir>`, and drive it through the engine's REPL file channel (`../krkrz_dev/src/core/doc/REPL.md`: write TJS to `<dir>/cmd.tmp`, rename to `cmd`, read and delete `<dir>/resp`). REPL commands are evaluated as one expression: wrap statements in `(function() { ...; return x; })()`, or only the first one runs; TJS has no closures (an inner function can't see the outer locals) and no `finally`. Injected keys don't change `System.getKeyState`, and KAG checks Return/Space with `getKeyState` (`checkProceedingKey`), so a `keyDown`+`keyUp` in one command does nothing: press with `keyDown`, wait a frame, then `keyUp` (the smoke test's `key()`), or click with `Agent.click`. Holding a key (Ctrl, R2) can't be simulated. Under the offscreen driver `Agent.captureScreen` returns black with the default GL draw device, so render `kag.primaryLayer` into a new Layer with `piledCopy` and `saveLayerImage(path, "bmp")` (that BMP's header says the pixels start at byte 56, but they start at 54; BGRA, bottom-up). `piledCopy` reads the layer buffers, so it hides anything that never reached the screen (a missing `update()`). To see the real frame, add `-drawdevice=sdl`, then `kag.setZoom(1, 1), kag.setInnerSize(1920, 1080)` and `Agent.captureScreen(path)` (a PNG written on the next frame). `Agent.click` takes window coordinates: the offscreen window is 1024x768 with the 1920x1080 game letterboxed into it.
- `savedata/*.ksd` persists system/scenario variables (`sf.*`, `scflags`) between runs, including things like the saved full-screen preference. When a config change appears to have no effect, stale savedata is a likely cause.

## Layout and load order

- `template/` — the reusable KAGEX framework. `template/system/*.tjs` is the whole runtime (~60 files); the other `template/*` folders are empty placeholders for a new game.
- `data/` — the sample game. In this repository it has no `system/` of its own: `data/startup.tjs` runs `data/system/Initialize.tjs` when there is one, and otherwise adds `../template/system/` to the auto path and executes `../template/system/Initialize.tjs`. The platform builds copy `template/system` into the package as `data/system` (a browser or phone build has nothing outside `data/`); the zip packages keep `template/` next to `data/`. Shipping a real game means copying `template/system` + `template/startup.tjs` into `data/`.
- `doc/` — the KAGEX reference, in English: `kagex.txt` (new/changed tags vs. stock KAG3), `action.txt` (action system), `world.txt` / `world_inst.txt` / `world_use.txt` (World extension: `envinit.tjs` schema, character/stage/time tags). Read these before changing tag behavior; stock KAG3 knowledge alone is not enough.

`template/system/Initialize.tjs` drives everything, in this order:

1. Registers auto paths: `data/` then a fixed list of subfolders (`video, others, rule, sound, bgm, fgimage, bgimage, scenario, image, system, voice, face, init, sysscn, main, evimage, thum, uipsd, effect`), each also accepted as a `<name>.xp3` archive beside the `data.xp3` the game was read from (`KAGArchivePath`, since 0.9.2: next to the executable, or in a macOS app's `Resources`; the executable's folder when the game runs from a folder or bound data; patches stay beside the executable). **Later-registered paths win**, so anything under `data/*` shadows the same filename in `template/system/`. Storage lookup is by bare filename across all auto paths — filenames must be globally unique unless shadowing is intended.
2. Runs `Storages.tjs` (`data/main/Storages.tjs`) — add nested asset folders there via `setupSubFolders([...])`; a new top-level folder outside the fixed list is not searched.
3. Links plugins (see below), then loads `AppConfig.tjs` (optional) and `Config.tjs`, then `Language.tjs` (`KAGLanguage`, from `Config.tjs`'s `KAGLanguageList`; see Languages below).
4. Loads the system classes, then `Override.tjs`, creates the `kag` window, attaches `KAGWorldPlugin` (`world.tjs` + `KAGEnv*.tjs`, configured by `envinit.tjs`), runs `AfterInit.tjs`, and finally `kag.process("first.ks")`.

In the sample, the game-side hooks all live in `data/main/`: `Config.tjs`, `Override.tjs` (class/function overrides, loads `MyHistoryLayer.tjs`), `AfterInit.tjs` (key bindings etc.), `envinit.tjs` (World definitions: times, stages, characters, poses), `first.ks` → `logo.ks` → `title.ks`, the system-menu scenarios (`config.ks`, `save.ks`, `load.ks`, `cgmode.ks`, `musicmode.ks`, `replay.ks`) and their CSV lists. Story/demo scripts are in `data/scenario/` (`s0001.ks` is the demo menu). Prefer these hooks over editing `template/system/` when a change is game-specific.

## Platform builds

The Windows and Linux zips come from the release workflow, which builds krkrz_dev itself. Unless an earlier release built the same engine the `windows` and `linux` jobs skip the compile: `.github/release-build/engine-build.sh find` (on `ci/windows-release`, where the release workflow lives) reads the note `kagex-engine-build.json` that every `publish` job now adds, listing the `krkrz_dev`, `xp3crypt` and `scnfile` commits its engine packages were built from, and unpacks that release's `kagex_engine_<platform>[_debug].zip` into `stage/` (the clone, vcpkg, configure and build steps guarded by `if: steps.engine.outputs.reuse == ''`; `Install and package` copies `stage/` as it is when `ENGINE_REUSE` is set and drops the package's own `engine.json`, and `key-slots.py` checks the slots in the binaries as before). A release with no note is refused, not guessed, so the first run after one is missing builds once and writes it, and reuse begins with the next release. The platform builds of `platforms.yml` reuse engines the same way (since 0.14.0), keyed by content rather than by commit: `.github/platforms/platform-engine.py` hashes what goes into each platform's engine (the pinned commits from the job's environment; the kit config without its version and comments; the files the build reads, as listed in its `PLATFORMS`; and the whole of `platforms.yml`, so any change to the workflow builds every engine once), and the `publish` job writes each job's key (artifact `kagex-engine-key-<platform>`: steam, web, android, ios, macos) into the note's `platforms`. A job whose key an earlier release's note has takes that release's `kagex_engine_<platform>.zip` and adds the game as the kit does after its build: the Linux kit's `make stage package` on the package unpacked as `build/linux/install`; the web kit's `stage_web.py` with the package's `krkrz.js`/`.wasm`/`.data` and its page as `krkrz.html` (the coi tag isn't added twice; `web-static-host.py` sets the page up again; the Web Core comes from the private SDK through `build.py`'s `web_setup`); Gradle on the Android package's project (`assembleDebug` for the emulator's REPL with the engine of `kagex_engine_android_debug.zip`, the debug APK's, since the kit compiles the REPL into Debug builds only and a debug APK of the release engine had none; `assembleReleaseDebugSigned` for the package with the release package's engine; `APP_CONFIG_FILE` is `app-config.json` with the engine's assets from the package's `engine-assets`); the game, version and an ad-hoc signature put into the iOS package's Simulator app; and the macOS package's app through the job's own "Put the game in the app". The Android and iOS jobs' engine packages are then the reused ones with `engine.json`'s version changed (`platform-engine.py version`). The smoke tests are the same either way. `[rebuild]` in a pushed message, the `rebuild` input or the repository variable `KAGEX_PLATFORM_REBUILD=true` (releases) builds every engine; `[reuse: <tag>]` or `reuse_from` takes that release's packages whatever their keys, to test the reuse steps (refused in a release). Releases before 0.14.0 have no platform keys, so the first release after them builds every engine. The other packages come from Wamsoft's platform kits, which build krkrz_dev without changing it, from configs at the repository root: `linux-config.json` (krkrz_linux: a Linux folder built in Valve's Steam Linux Runtime 3.0 "sniper" container), `web-config.json` (krkrz_web), `app-config.json` (krkrz_android) and `ios-config.json` (krkrz_ios), with this repository as `PROJECT_DIR` and `KRKRZ_BASE` the folder that holds `krkrz_dev` and the kit. macOS uses krkrz_dev's own `arm64-osx` preset. `.github/workflows/platforms.yml` builds and smoke-tests all five, with the engine (`21d20e9`, as for the zips), the kits and Emscripten (`EMSDK_VERSION`, 6.0.13: it was `latest` until 7.0.0 came out four minutes before 0.21.0's release run and the web build stopped at Effekseer's `malloc`) pinned in its `env`. It runs on pushes to `platforms/**` branches (`[platforms: linux web]` in the commit message builds only those, `[platforms: none]` nothing) and from the release workflow (`workflow_call` with the release commit as `ref`). In a release run any failed job cancels the whole run (its last step, `gh run cancel`, after it has pushed its results; the token needs `actions: write`), so a release that can't publish doesn't wait an hour for iOS and Android; on a `platforms/**` push every platform runs to the end. Each job uploads its build before the smoke test (`kagex-linux`, `kagex-web`, `kagex-android` (release) and `kagex-android-debug`, `kagex-ios-simulator`, `kagex-macos`) and force-pushes its logs, screenshots, an `<log>.errors` digest of each log and, on macOS, the engine's crash reports (`.ips`; a native crash's output is lost from the buffered log) to branch `ci/platform-results-<job>`; job logs themselves can't be read from this environment. `.github/workflows/pages.yml` puts a release's `kagex_sdl3_web.zip` on GitHub Pages (the release workflow starts it). The packages hold `data/` with `template/system` copied in as `data/system`, which `data/startup.tjs` prefers, and the sample's compiled scenarios (since 0.9.1): the `scenarios` job runs `.github/platforms/compile-scenarios.sh` (`-scncompile=all` with the engine of the newest release that has `kagex_sdl3_linux_release.zip`, so `.scn` with its scnfile) and uploads `kagex-scenarios`, which every platform job unpacks into its checkout. Where the data is read-only (`readonlydb`: web, Android, iOS) the game can't compile them itself, and without them it played the scripts, so Search, BACK and Replay's scenes did nothing there (0.9.0).

- **Plugin order.** List a krkrz_dev plugin first in a config's `plugins`: tp_stub's `krkrz.cmake` caches `NCBIND_DIR` relative to the first plugin folder that includes it, and with the kit's `virtualpad` first that was the kit's folder, which has no ncbind.
- **Linux.** `cmake.options` sets `CMAKE_CXX_STANDARD_LIBRARIES` to freetype's archives (png, zlib, bzip2, brotli) so they end every C++ link: the same krkr_richtext fix as the relink above. The smoke test runs the package on the runner itself, with Mesa's EGL installed. The kit's engine and plugins each carry their own static copy of libgcc's unwinder, so a C++ exception that unwinds through a plugin's frame aborts the game (`UPSTREAM.md`): the json plugin's `V2Unlink` throws on the way out, and every exit dumped core (exit code 134) until `KAGUnlinkPluginsBeforeExit` (`Initialize.tjs`) unlinked it first, before the framework's exits and from `KAGWindow.finalize`. krkrthreepp's `V2Unlink` (`unregisterThreeppWebApi`, a `TVPExecuteExpression` inside its own `catch (...)`) aborted the same way as soon as the plugin was linked, so it's unlinked there too, after the window's KAG plugins have let go of its objects (the engine leaves a plugin linked while any of its objects live: a test that kept a `Threepp.Scene` in a global still aborted). `smoketest.py` quits each desktop run through `kag.shutdown()` and wants exit code 0 (`quit_check`); the smoke tests otherwise stop the engine with a signal, which hid it. The SDK's compiler links libstdc++ into every plugin, and its symbols were exported, so a plugin loaded later bound to an earlier one's copy (`LD_DEBUG=bindings`: krkrthreepp's locale facet ids went to `liblayerExSave.so`) and krkrthreepp crashed compiling a `std::regex` in its first shader: `cmake.options` links every shared library with `-Wl,--exclude-libs,ALL` (`CMAKE_SHARED_LINKER_FLAGS`, `CMAKE_MODULE_LINKER_FLAGS`), which keeps a static library's symbols inside its plugin.
- **Web.** krkr_richtext doesn't compile for wasm32 at engine 2.6.5 (its `main.cpp` casts a `tTJSVariant` to `tjs_intptr_t`, which tp_stub only converts to on Apple or where `intptr_t` is `int64_t`), so the web build draws text with `drawText`. `.github/platforms/web-plugins.py` edits krkrz_web's built-in plugin list in the CI checkout, dropping the plugins from Wamsoft's private repositories and adding krkreffekseer, with `krkreffekseer-kit.cmake` at the end (the same EGL and UTF-helper workarounds as Android, below). Effekseer's GLES 3 renderer maps its vertex buffers with `GL_MAP_UNSYNCHRONIZED_BIT`, which WebGL can't do: Emscripten's `glMapBufferRange` returned 0, Effekseer `memcpy`'d into it, so nothing drew and the engine's low memory got overwritten (later steps of the smoke test hung). `krkreffekseer-webgl.cpp` swaps the bit for `GL_MAP_INVALIDATE_RANGE_BIT` through `glad_glMapBufferRange`, renamed for `efk_renderer_gl` only. The site downloads files on demand (`web://`), and the save folder (`user://`) is SDL storage rather than local files (see the bookmark notes under the BMP bug). `lowercase` puts the files in lower case for case-sensitive hosts such as GitHub Pages, and `coi-serviceworker.js` supplies the COOP/COEP headers there. `.github/platforms/web-static-host.py` readies the site for a static host, in the staging step and again in `pages.yml` (0.2.0's zip lacks both changes): the engine reads the `web://` file list from `gamedata/krkrz_files.json`, which the kit writes to `gamedata.krkrz_files.json` and only its `serve.py` answers with, so it copies the file there (without it Pages stopped at `Config.tjs not found`); and coi-serviceworker reloads the page on `updatefound`, before its worker is active, so on Pages the reloaded page was sometimes left uncontrolled and not `crossOriginIsolated` (`SharedArrayBuffer transfer requires self.crossOriginIsolated`, nothing starts until the visitor reloads), so it sets `window.coi.doReload` to wait for `navigator.serviceWorker.ready`. It also adds the home-screen setup: iPhone browsers have no element full screen (the engine's request just fails there), so `apple-mobile-web-app-capable` makes the page open without Safari's bars from the Home Screen, and `manifest.webmanifest` (full screen, landscape) does the same for Android's Add to Home screen; the icons are `platform/web` (`make_ui.py icons`), the names `linux-config.json`'s `name` and `ios-config.json`'s `displayName`, which also replace the kit's `<title>krkrz</title>`. Its head tags sit between `<!--kagex-head-->` and `<!--/kagex-head-->` (older sites' tags without the markers are removed), so it can run again: `pages.yml` reruns it on the release zip with `--url` (from `actions/configure-pages`) for the link previews (Open Graph and Twitter card: name, description, `platform/web/preview.jpg` from `make_ui.py preview`; Discord and the like need absolute image URLs). **Updates** (since 0.3.1): the engine caches every `web://` file in OPFS under a key made from its relative URL alone (`krkrzOpfsKey`: SHA-256 of `gamedata/...`), never checks it again, and shares that cache with every krkrz game on the origin (all of itch.io's HTML5 games share one), so an updated site kept serving players the old files. `web-static-host.py` gives the site a build id (a hash of its files) in `kagex-build.json` and `<meta name=kagex-build>`, with `?v=<id>` on `kagex-web.js`, `webconfig.js` and `krkrz.js` (krkrz.js's pthread workers load the same URL). `platform/web/kagex-web.js` (loaded before `webconfig.js`) adds a `Module.preRun` run dependency that reads `kagex-build.json` with `cache: no-store`, reloads a stale page once (`sessionStorage` guard), and empties the OPFS cache entries (`/^[0-9a-f]{40}_/`) when the build differs from the `.kagex-build` marker there; it also wraps `window.fetch` so same-origin fetches without `?v=` revalidate (`cache: no-cache`); the engine fetches on the main thread (Asyncify). The same file shows the **Add to Home Screen** bar on phones and tablets outside the installed app: `beforeinstallprompt`'s prompt behind an Add button where the browser fires it (Chrome, Edge, Samsung Internet, Opera), the Share steps on every iOS browser, the menu steps on other Android browsers (after 2.5 s without the event); closing it hides it for 30 days (`localStorage`), and it goes 10 s after the game starts; English or Japanese by `KRKRZ_LANG`. **Typing on phones and tablets** (since 0.18.1, coarse pointers only): a phone's browser opens its keyboard only for a field the page focuses while it handles a tap, and SDL's web port has none, so on `touchend` (capture, on the window) `kagex-web.js` asks the game through `krkrz_repl_eval` (`KAGTextEntryWebTap` in `TextEntry.tjs`: the [edit] field the tap went down on, which SDL's touch events delivered already, as `<maxChars>:<UTF-16 hex>`), `preventDefault`s the tap (its emulated mousedown would focus the canvas, `tabindex=-1`), focuses a hidden `<input>` with the text selected, stops its key events from reaching SDL (which listens on the window) and hands every `input` to the game (`KAGTextEntryWebInput`, hex) and Enter or blur (`KAGTextEntryWebDone`); the bridge calls only note values, a game `Timer` applies them. A browser lets nothing outside the full-screen element take the focus (`focus()` silently did nothing while the canvas was full screen), so on those devices the canvas's `requestFullscreen` asks for `document.documentElement` instead; the page's style fits the canvas either way. `WebEngine(touch=True)` (`--touch`) is Chromium with touch emulation; `touch_hold` sends a held tap through CDP (`Input.dispatchTouchEvent`), since Playwright's `tap` ends the touch before the engine's loop has seen it start. On Android and iPad, full screen from Config works, but the engine makes the request from its own loop, so the browser defers it to the next tap. The web smoke test serves the site with `python3 -m http.server`, as Pages does, rather than `serve.py`, and `pages.yml` runs it on the live site after each deploy (`ci/platform-results-pages`). Headless Chromium lets the page go full screen without a click, and the full-screen canvas covers the loading screen, so a first visit screenshots black there; a real browser refuses that and shows "Click / tap to start" (add an init script that rejects `requestFullscreen` to see it). The build has no `Agent` class: the smoke test posts keys with `kag.postInputEvent` and runs every command from a `Timer`, because a scenario load started inside a `krkrz_repl_eval` call crashed the page. **The file cache and the prefetch:** krkrz.js's prefetch (the `krkrz_prefetch.json` list kagex-release writes, two workers from a second after the runtime is up) makes each OPFS entry with `getFileHandle(..., {create: true})`, an empty file, before it writes it, and the engine's `krkrz_web_fetch` takes any entry it finds as the file, so a file the engine read in between came back empty. A compiled script then failed: `TVPExecuteStorage` opens a script once as bytecode and, when that isn't bytecode, again as text, so the empty first read and the full second one made it parse the bytecode as text (`Syntax error (syntax error) at line 1` right after `KAGMainWindow constructor`, then the error dialog trapped: `RuntimeError: unreachable`, `null function`), and the page stopped; on the Linux runner kagex-release's web (files) test hit it in three runs of five (`UPSTREAM.md`). `kagex-web.js` now makes a lookup of an entry being written wait for the write (it wraps `FileSystemDirectoryHandle.getFileHandle` and `FileSystemFileHandle.createWritable`), and removes an entry a failed write left. Committing each OPFS write 1.5 s late (an init script delaying `FileSystemWritableFileStream.close`, `WebEngine`'s `init_script`) reproduced it every time; `tools/release/test/smoke.py` starts the files build that way too (`web_prefetch_race`). Playwright's sync API delivers console events only inside its own calls (`time.sleep` delivers none: wait with `page.wait_for_timeout`), and `WebEngine` writes each failed start-up poll into its console file, which smoke.py keeps even when the page never started.
- **Android.** `platform/android-res` (the `resOverride`) names the app in `values`, `values-ja`, `values-zh-rCN` and `values-zh-rTW`: the kit names it "krkrz" in all four. The kit asks Gradle for the SDK's CMake 3.22.1, but with krkr_richtext the engine downloads ICU with an option CMake 3.24 added (`DOWNLOAD_EXTRACT_TIMESTAMP`): CI installs the newest SDK CMake 3.x and changes `version` in the kit's `app/build.gradle`. There's no `a11y` plugin: it turns on `KRKRZ_USE_A11Y`, and at engine 2.6.5 the engine's AccessKit setup can't find its Android library (`find_library` in the NDK cross-compile), so `libkrkrz.so` didn't link. The x86_64 libvpx (for the emulator) needs `nasm`. The kit's `BootstrapActivity` asks for landscape in `onCreate`, which restarts it on a portrait device, and each `onCreate` started its own copy of the game files out of the APK: two at once left the engine without its data (`No project data`; `UPSTREAM.md` 33), so `kit-android-bootstrap.patch` (applied in `platforms.yml` and `live2d.yml`, so in the engine package too) runs the copy once at a time. krkreffekseer (Effekseer effects) is built in, with three CI-only workarounds that leave krkrz_dev as it is: `kit-vcpkg.py` adds minizip-ng to the kit's fixed vcpkg manifest (the kit doesn't merge plugin manifests); `krkreffekseer-kit.cmake`, appended to the kit's `CMakeLists.txt`, defines `<EGL/egl.h>`'s include guard for `efk_renderer_gl` (its `eglGetProcAddress` clashed with the plugin's GLES hook macro) and renames the plugin's own `TVPUtf8ToUtf16`/`TVPUtf16ToUtf8` (duplicates of the engine's once linked in); and `krkreffekseer-odr.cpp` defines Effekseer's in-class `static const` members, which the unoptimized debug APK odr-uses. The release workflow's Linux Debug build needs it too (a shared object links with them undefined, so 0.3.1's debug `libkrkreffekseer.so` didn't load): `release-build/krkreffekseer-odr.cmake` on `ci/windows-release` adds it to `efk_core` through `CMAKE_PROJECT_INCLUDE`. Since 0.4.0 the release stops when `libkrkreffekseer.so` doesn't load or a zip lacks krkreffekseer, and the zips' smoke test (`run-kagex.ps1 -Plan smoke`) plays the Effects demo and fails unless the effects drew. The smoke test drives the debug build through its REPL socket (`<applicationId>.repl`, forwarded with adb); the package is the kit's `release-debug` build (optimized, signed with the debug key).
- **iOS.** A Simulator build (a device build needs an Apple Developer team), Debug, without krkr_richtext (with it, CMake's Xcode generator stops with "duplicate object ids not allowed"; a bisect pinned it to that plugin) or krkreffekseer (the same error), so effects show nothing there, and with `a11y` off. krkrz_ios builds only the browser REPL (`-replweb`), which the smoke test drives through `POST /pad/exec`. Screenshots of the Simulator come out black on the CI runners, even through `Agent.captureScreen`, so there the smoke test checks the game's state only.
- **macOS.** The macOS runners' CMake 4 needs `CMAKE_POLICY_VERSION_MINIMUM=3.5` (set for every job). Effekseer's GLES 3 renderer on Apple returns a null `glMapBufferRange` unless `GL_ARB_map_buffer_range` is defined, and copied into it, so the first effect drawn crashed the engine: the configure step passes `.github/platforms/krkreffekseer-apple.cmake` as `CMAKE_PROJECT_INCLUDE`, which defers (`cmake_language(DEFER)`) defining that macro for `efk_renderer_gl` until the targets exist. The job renames the app to `KAGEX.app`, copies the game into `Contents/Resources/data`, sets the name, bundle id, version and icon, and signs it ad hoc again: adding the files broke the build's own signature, which macOS reports as a damaged app. Its smoke test runs with SDL's cocoa driver; the offscreen one has no OpenGL ES there.
- **xp3crypt and scnfile** (since 0.9.0): kagex's own plugins, [krkren/xp3crypt](https://github.com/krkren/xp3crypt) (encrypted `data.xp3`, built into every engine so its XP3 filter is in place before `startup.tjs`) and [krkren/scnfile](https://github.com/krkren/scnfile) (compiled scenarios), are in every package's engine, so kagex-release's archive and scenario encryption work with the released engines; kagex-release writes each game's keys into them. Their commits are pinned as `XP3CRYPT_SHA`/`SCNFILE_SHA` in `platforms.yml`, `release-tool.yml` and the release workflow, and `setup.sh` clones them next to krkrz_dev. The kit configs list their `plugins/` folders after krkrz_dev's, the plugins after krkrz_dev's and `xp3crypt` in `staticPlugins` (Linux; Android and iOS link every plugin statically); `web-plugins.py` adds both to krkrz_web's list. krkrz_dev's own builds (the zips, macOS) take `-DTVP_PLUGIN_FOLDERS=<xp3crypt>/plugins;<scnfile>/plugins -DTVP_PLUGINS=xp3crypt;scnfile -DTVP_PLUGINS_STATIC=xp3crypt` plus `-DTPSTUB_DIR`/`-DNCBIND_DIR`/`-DSIMPLEBIND_DIR` set to krkrz_dev's: those `-D` lists come before krkrz_dev's own, and tp_stub's `krkrz.cmake` caches the three relative to the first plugin that includes it (a missing `xp3crypt/plugins/ncbind`), the same trap as the kits' plugin order above. On the desktops scnfile is a plugin library of its own; where every plugin is static (web, Android, iOS) static plugins are linked whole (`--whole-archive`/`-force_load`), and both plugins compile Monocypher, so `monocypher-kit.cmake` (appended to the kit's `CMakeLists.txt`) force-includes `scnfile-monocypher-names.h` into scnfile, renaming its copy's `crypto_*` names. `smoketest.py --encryption required` (every platform job) checks `XP3Crypt.installed` and an `SCNFile` round trip; `release-tool.yml` builds the tool with both (`KAGEX_RELEASE_REQUIRE_ENCRYPTION=1` makes `smoke.py` check it can encrypt), and the release's `tool-check` builds and runs the sample encrypted, then with hidden names, then signed with hidden names and signed without, checking the build result's `protection` (`archive`: plain, encrypted or names hidden; `scenes`; `signed`) and that `data.xp3` holds no plain script text.
- **Smoke test on the platforms.** `--target android|ios-sim|web` runs the sample's steps; clicks go through `kag.onPrimaryClick` because `Agent.click` takes window coordinates, which differ on every platform. A save failure leaves the save-failed message open, which then swallows Return, the arrows and the pad buttons in later steps.

## The release tool (tools/release)

`kagex-release` packages a game for every platform (`tools/release/README.md` is the user-facing description). It is an appserve app like krkrz_tools' tools (a local HTTP server and a browser app window; `web/` is the screen, embedded in the exe) and a CLI (`--cli init|check|plan|build|keygen`). It links krkrz_tools' libraries (`krt_app`, `krt_xp3`, `krt_audio`, `krt_image`, `krt_loop`, `krt_release` on Windows) through `add_subdirectory(KRKRZ_TOOLS_DIR ... EXCLUDE_FROM_ALL)`, by default `../krkrz_dev/src/tools/krkrz_tools`; CI clones the krkrz_tools commit `ENGINE_SHA` pins. Its vcpkg manifest is `tools/release/vcpkg.json` (krkrz_tools' dependencies plus `drlibs` for dr_flac). The libraries' own error messages are in Japanese.

- **Source.** `main.cpp` (CLI, the window's API: `/api/release/state|open|check|host|save|build|reveal|keygen`, builds as a `JobRunner` job), `Settings` (release.json: defaults from `first.ks`'s `sf.software_*` and `krkrz.cf`, `withDefaults` merging, `validate`), `Project` (finds the folder with `data/startup.tjs`, from the path given, the current folder or the exe's parent), `Host` (per-platform requirements: a Mac, Xcode via `xcrun --find actool`, signing identities via `security find-identity`, Java 17 from `JAVA_HOME`/PATH, the Android SDK), `Plan`, `Build`, `Media`, `Layered` (splitting `.psd`/`.clip` files), `Engine`, `Archive` (zip with ZIP64/Unix modes/symlinks, tar.gz with pax headers, SHA-256), `Icons` (area-averaged sizes, `.ico` with PNG entries, `.icns`), `Keys` (the keys file), `Sign` (signing through krkrz_tools' `krt::sig`), `Encrypt` (xp3crypt), `Scenes` (scnfile), `Scripts` (TJS bytecode), `LipTracks` (lip tracks' headers, and the ones whose voice changed: a warning of `validate`), `Subprocess`. All but `main.cpp` make `kagex_release_core`, which kagex-lipsync links too. Not `Process.h`: on Windows that name shadowed the C runtime's `<process.h>` (`_beginthreadex` not found). Don't name a function `linux` (a GCC macro).
- **Engine packages.** `kagex_engine_<platform>[_debug].zip` (debug for Windows and Linux only; Android's debug package is only for `platforms.yml`'s reuse), downloaded from the release tagged with the tool's version (`KAGEX_RELEASE_ENGINE_URL` overrides) into the cache (`%LOCALAPPDATA%`, `~/Library/Caches`, `$XDG_CACHE_HOME` or `~/.cache`, then `kagex-release`; `KAGEX_RELEASE_CACHE` overrides), or taken from `--engines`/`KAGEX_RELEASE_ENGINES` (made absolute against the current folder: the Windows resource step resolves `krkrz.exe` against the package's folder, and a relative unpacked package failed there up to 0.9.3), else from `engines/` next to `data/` (`localEngines`). Each has an `engine.json`. `scripts/engine-package.py` makes the desktop and web ones from the release packages (without the game; symlinks dereferenced; the macOS app without signature, `data/` or `.cf`; the web site without `gamedata/` and its lists); `scripts/android-engine.py` makes Android's from the kit checkout and the release APK (with `--debug`, `kagex_engine_android_debug.zip` from the debug APK, whose engine must have the REPL); `scripts/ios-engine.py` makes iOS's from an unsigned device build and the Simulator app. `platforms.yml`'s Android and iOS jobs upload `kagex-engine-android`/`kagex-engine-ios`.
- **Build.** The game's files are staged in `<output>/.work/data` as hard links (copies where links fail), so nothing may write to a staged file: replace it (remove, then write). Media conversion runs there (`Media.cpp`: parallel, cached by content hash plus settings in `<cache>/media`; a file whose new name another file already has stays as it is, unless that file was converted from one of the same name (a language folder's `lang/ja/start_over.png` beside `image/start_over.png`: until `made` counted those, the language's images stayed PNG and the converted-game test found `start_over.png`); images are decoded to tell opaque from transparent; FLAC through dr_flac; `.sli` rescaled to 48 kHz for Opus; names written with an extension in `.ks/.tjs/.csv/.txt/.asd/.json/.func` scripts, printf patterns like `ai%s%06d.wav` included, keep their files unless rewriting is on; scripts are matched as UTF-8, UTF-16LE or Shift_JIS without matching inside a double-byte character), then `data.xp3` is packed once. The `.cf` next to the engine is the developer's `krkrz.cf` minus `orgname`/`appname`/`debugwin`, plus those. Android, iOS and the web read no `.cf` beside an executable but a `config.cf` in their resources (`TVPGetEmbeddedOptions`: the APK's `engine-assets/config.cf`, the app's `config.cf`, the site's `resource/config.cf`, listed in `resource.list`), so `resourceConfig` puts the developer's options and `debugwin=no` at the top of the package's own (the engine takes the first line of a name; without `orgname`/`appname`, which on iOS would move earlier builds' saves), and the web, whose command line (`KRKRZ_WEB_DEFAULT_ARGS`) comes before `config.cf`, drops the package's arguments the game's `krkrz.cf` sets. Binding appends the xp3 at a 16-byte boundary after the executable (the SDL engine looks after the image end, after `data.xp3` and before `data/`). **Archives** (`packArchives`, since 0.9.2): every Windows, Linux, Steam and macOS build with `xp3`/`bind` data is split as Wamsoft's games ship: `data.xp3` keeps `startup.tjs`, the top-level files and the folders a signed build reads before it has verified the rest (`system`, `main`, `init`, `sysscn`), and each folder of `splitFolderNames()` (`Plan.cpp`: the rest of `Initialize.tjs`'s list, by exact name) the game has becomes `<folder>.xp3` beside it (macOS only with a framework that has `KAGArchivePath`, `frameworkFindsSplitArchives`). The web, Android and iOS get the whole data in one `data.xp3` (`xp3Whole_`, `xp3For(id)`). The split folders are renamed out of the stage while `data.xp3` is packed and back after, so a platform with `folder` data still gets them. Encrypted archives each get their own salt range (xp3crypt's `saltBase`, `0x01000000` apart). **Hidden names** (`archive.hideNames`, since 0.9.2 in `data.xp3`; 0.9.0 and 0.9.1 shipped `data.xpc` with a loose `data/startup.tjs`): every archive is packed with hashed names (xp3crypt `--hash`), but `data.xp3`'s `startup.tjs`, which is `system/hashed-bootstrap.tjs` (compiled with the other scripts; xp3crypt's `plainNames`): the engine opens `data.xp3` as usual and runs it, it mounts `data.xp3` itself as `xpcrypt://data/` (`kagexHashedArchive`), and `Initialize.tjs` mounts each media archive as `xpcrypt://<folder>/` (`KAGMountHashedArchive`). The game's own `startup.tjs` goes into `data.xp3` as `startup-game.tjs` (hashed), which 0.9.4's bootstrap (`kagexHashedLayout = 3`) runs after mounting; for an older bootstrap (`frameworkRunsGameStartup` false) it is set aside as before, the bootstrap runs `Initialize.tjs` in its place, and `validate` warns. The hashed archives' indexes are uncompressed (the plugin has no zlib). `frameworkHidesNamesInXp3` (`kagexHashedLayout` in the bootstrap) gates it. On the Windows host `krt::release::run` sets the icon and version strings (it shrinks the exe: the PNG icons are smaller). The macOS app's `.cf` is `Contents/MacOS/krkrz.cf`, its data in `Contents/Resources`; `Info.plist` is XML there. Web: the page as `web-static-host.py` makes it (the same head block, with the game's title, `platforms.web.description`, `preview` (default `platform/web/preview.jpg`; the icon without one) and `url` for the previews, the manifest, `kagex-web.js` built into the tool from `platform/web` by `CMakeLists.txt` (`KagexWebJs.h`), the build id); `gamedata/` in lower case with `gamedata.krkrz_files.json` (also as `gamedata/krkrz_files.json`) and `krkrz_prefetch.json`; `krkrz.data` is the engine's preloaded `/data.xp3` and its size is written into `krkrz.js` (`files:[{filename:"/data.xp3",start:0,end:N}],remote_package_size:N`): emptied for the files mode, the game's xp3 in the xp3 mode (`KRKRZ_WEB_DATA_XP3`, no webbase); `KRKRZ_WEB_PROJECT_XP3` is always false (the sample site's `gamedata/data.xp3`, which 0.13.2's engine package carried as true, so its files-mode games opened `web://./data.xp3>` and stopped at `Cannot find storage`; `engine-package.py` writes false now). Android: the Gradle project in `.work/android` gets the game's `app-config.json` (assets: `engine-assets/` plus the data), a `res-override` (app name in `values`, `values-ja`, `values-zh-rCN`, `values-zh-rTW`; the icon as an `<inset>` of a bitmap for the adaptive icon's foreground and monochrome), `app/src/main/AndroidManifest.xml` with the text-to-speech `<queries>` (`ttsQuery`, since 0.17.0) and the game's `manifestAdditions`/`applicationAdditions` inserted (`androidManifestInto`; the kit's `build.gradle` makes its manifest from that file; `check` runs `xmlFragmentProblem` on them), `local.properties`, and `gradlew :app:{assemble,bundle}{Release,ReleaseDebugSigned}` with `PROJECT_DIR`, `JAVA_HOME`, and `RELEASE_STORE_*` from the window's password prompt or `KAGEX_ANDROID_*_PASSWORD`. iOS: `Info.plist` through `plutil` (binary in the bundle), the icon through `actool` and PlistBuddy's Merge, the profile's entitlements via `security cms -D` (an unsigned plist profile is taken as it is, for tests), nested code signed first.
- **File lists and patches.** After the media conversion every build writes `<output>/<exe>-<version>-files.json` (the staged files, `/`-separated, with SHA-256s; `fileList` in `Build.cpp`). With `output.patchFrom` (a list, relative to the project) it also writes `<output>/<exe>-<version>-patch/patch.zip` of the staged files that are new or changed (hard-linked into `.work/patch`, zipped with `zipFolder`), reported as an output with platform `patch`; then no platform has to be enabled (`validate`, `execute`), though compiling the scripts still takes the host's engine. `contents.exclude`'s defaults (`defaultExclude` in `Settings.cpp`) are `*.bak`, `*.tmp`, `Thumbs.db`, `desktop.ini`, `.DS_Store`; up to 0.9.2 they had `*.psd` and `*.clip` first, and `loadSettings` replaces a saved list that is exactly that old one. `collectGameFiles` (`Plan.cpp`) puts back a `.clip`/`.psd` an exclusion matched when a script names it after `clip://`/`psd://` (`layeredFilesNamed`; UTF-16LE scripts converted, others read as bytes), or when it's a pose `charinit.csv` names (`<files>.psd`, `<files>_*.psd`, `.clip` too; `charinitFiles`/`namedByCharinit`) without a `.txt` of the same stem, with a framework that reads split files (`frameworkReadsSplitLayers`); with such a framework it also leaves out a `.psd`/`.clip` whose layers the game has already, a layer structure of its stem (`isLayerStructure`: the first line that isn't a `#` comment is psdlayer's canvas line, four empty fields then width and height), listed through `shadowed` and noted by the build. `test/smoke.py`'s `patch_tests` builds a patch from an empty list, then from that list after changing the project, without engines (and so with `compileScripts` off).
- **Split PSD and CLIP files** (`Layered.cpp`, since 0.11.0; README "Photoshop and CLIP STUDIO PAINT files"). Right after `stage()`, before `media()`: every staged `.psd`/`.clip` is replaced (unlinked, the stage holds hard links) by `<stem>.txt`, psdlayer.tjs's layer structure (UTF-8 with a BOM, a `# The layers of a .psd file, split by kagex-release` line (not the file's name: the cache shares splits by content), the canvas line, then normal layers and folders interleaved in descending layer index, as `loadPSD` meets them), and `<stem>_<layer id>.tlg` (TLG6, or TLG5/PNG when *Media* converts to those, so `media()` skips them), and `media()` converts them on (JPEG). It links krkrz_tools' `psdparse` and `clipparse` (the libraries psdfile and clipfile wrap) and mirrors the plugins exactly: psdfile's `convBlendMode` and `assignAutoIds` (ids for `-1` layers from the largest id, in file order), `getLayerImage(..., BGRA_LE, IMAGE_MODE_MASKEDIMAGE)`; clipfile's `clipCompositeToTjsType`, `opacity*255/256`, `layerImage(IMAGE_MODE_MASKED)` RGBA to BGRA; folders by `parent` id, adjustment layers, a PSD's text/fill/divider layers and empty layers left out (the runtime's `loadPSD`/`loadCLIP` leave them out too). Cached by content in `<cache>/layers`. Since 0.9.3's defaults keep `.psd`/`.clip` files, every one the game has comes this way. A file that can't be read (the test projects' `layers.psd` is just `8BPS`) goes in as it is, with a note, as the media conversion keeps a picture it can't read. A staged `<stem>.txt` that isn't a layer structure, a picture `<stem>_<number>.<image ext>`, or two layered files of one stem stop the build (a `.txt` that is one left the file out already, in `collectGameFiles`). With a framework that doesn't read split files (`frameworkReadsSplitLayers`: `affineLayeredFromPieces` in `AffineLayer.tjs`, `findStandLayerFile` in `KAGEnvCharacterEx.tjs`) the files go in unsplit, with a note. The plan's `splitLayered` counts them; `--cli split <file> <folder> [--format=]` writes one file's split. `test/smoke.py --tests layered` writes Pip's levels as PSDs (`tools/assets/psdwrite.py`), checks the patch build reproduces `pip_*.txt` and every picture, then (Linux, `--engines`) runs `smoketest.py --packaged --clip required` on the package.
- **Compiled scripts** (`Scripts.cpp`, `contents.compileScripts`, on by default). After the media conversion every staged `.tjs` is replaced by TJS2 bytecode (`TJS2100\0`), which the engine's `TVPExecuteStorage` tells by its header (`startup.tjs` too; checked on the Linux and web engines). The host's engine package (on macOS a copy of its app, signed ad hoc: unsigned it doesn't start) runs headless with `.work/` as `-datapath`, `-forcelog=clear`, the project's `readencoding` from `krkrz.cf`, and a generated `compile/startup.tjs` that reads `compile/list.txt` (`@set` lines, then `<id>\t<script>\t<probe>\t<marked>\t.`) and writes `compile/result.txt` (UTF-16LE); the engine's output goes to `<output>/compile-scripts.log`, and the `... at line N` after each `kagex-compile <id>` marker gives a compile error's line (the exception has none). Bytecode keeps the mode it was compiled in, and `evalStorage` of source is `return <text>;`, so a script that is one expression is compiled as one: the probe, `(` + the script with its trailing `;`s blanked (not cut off, so nothing the scan misread is left out) + `)`, compiles only then (a named function declaration isn't an expression; `envinit.tjs` ends with `];`, so it also compiles as statements, with a void result). Files are compiled in the order the game reads them (`startup.tjs`, `Initialize.tjs`, `Storages.tjs`, `AppConfig.tjs`, `Config.tjs`, the rest by name) after `@set (PACKED=1)` (and `DEBUG=1` with `engine.debug`), so their `@set` lines carry over as at run time. Engine bugs (`UPSTREAM.md`): debug information makes the engine dump core when it reports an exception, so there is none (traces say line 1); LP64 engines cut integer constants beyond 32 bits (`0xff000000` loads as -16777216). A canary (`0x123456789`) shows whether this engine does; then each script with such literals is compiled again with marker numbers in their place (from `0x4B580000`, unlike any literal in it or its cut value; `-M` stands for `-v`), and `fixWideConstants` moves each marked slot to the LONG table after checking the two compiles match everywhere else, so a scanner mistake (say, inside a string) shows as a difference and keeps the script source rather than changing it. Constants the compiler folds (`literal op literal`, a literal in `@"${...}"`, which becomes part of the string) can't be marked, so those scripts stay source there. `tjs::scan` follows tjsLex.cpp: block comments nest, `@` directives are skipped, a regex (after a non-operand) ends at the first unescaped `/`, `<%...%>` octets, Shift_JIS second bytes (`\` is one). The bytecode's indexes are int16 (`tooLarge`). It has no form for a constant object either: `(const) [...]`/`(const) %[...]` compile to null without an error, so a script with `(const)` (`Scan.constObjects`) stays source (`MainWindow.tjs`'s shortcut table is a plain dictionary for that). Compiling is deterministic, so a patch holds only the scripts that changed. `test/smoke.py`'s `script_tests` builds a game whose scripts check the constants, expression scripts and UTF-16LE/Shift_JIS scripts as it runs, then a patch.
- **Compiled scenarios** (`scenes.compile`, `scenes.encrypt`; `Builder::scenes` and `scenesInto` in `Build.cpp`, `Scenes.cpp`). After `media()` and before `signStage()` (a compiling run of a signed game would refuse its options) and the compiled scripts (it runs the source): the staged `*.scn`/`*.scn.json` are unlinked (hard links to the developer's), the host's engine package runs `<stage> -scncompile=all -datapath=<work>/compile/save/` (Linux with the offscreen driver), the console log goes to `<output>/compile-scenarios.log` and its `Compiled scenarios:` line decides success; each `.scn` is sealed (remove, then write), and the compiled scripts plus their translations (`lang/<code>/scenario/<script>`, built into them) and `parsermacro.ks`/`parseroption.txt` are removed (`!scnlist.txt` stays: `isSceneListed` reads it). `.scn.json` (the host engine lacks the plugin) with `scenes.encrypt` is an error. `scenesInto(id, root)` runs on each platform's own copy right after its engine files land (Windows/Linux after `pluginsInto`, macOS before `macSign`, the web before `webPage`'s build id, Android after copying the project, iOS before signing): it scans binaries (`.so/.dll/.dylib/.wasm/.exe`, extensionless ELF/Mach-O; not `data/`, `gamedata/`) for the slot marker (one per file, or one per slice of a fat Mach-O), fails the platform when there's none and the files are `.scn`, and writes the key in place. The tool contains no marker itself (scnfile keeps it inverted). `SCNFILE_DIR` (default `../scnfile`) adds scnfile's `seal.cpp`, `seal_random.cpp`, `psb.cpp` and Monocypher (`KR_HAVE_SCNFILE`), but not its Monocypher when xp3crypt's library is built in (one copy: two clash at link time); without scnfile `scenes.encrypt` is refused. The default for `compile` is on when the game has a `!scnlist.txt` and its framework has `SceneParser.tjs` (`Project::sceneList`, `frameworkCompiles`). The 0.8.0 engine packages have no scnfile (nor xp3crypt), so with them the sample compiles to `.scn.json` (0.9.0's have both); local tests use 0.9.0's or later, or an engine package folder with `plugin/libscnfile.so` added (`--engines`, or `engines/` in the project: a build that silently used the cached 0.8.0 engine got `.scn.json` and then refused to encrypt). `checkPlatform` notes which format this computer's engine compiles to and fails a desktop platform whose engine lacks the plugin when it's `.scn`; the plan has `scenes.format`; `validate` refuses `scenes.encrypt` when the host engine is here without the plugin. These look only at engines already here (`engineIfPresent`: a local folder, an unpacked local zip, the cache) and at plugin file names (`engineHasScnfile`). `test/smoke.py --tests scenes` covers both cases (and runs `tools/smoketest.py --packaged` on the encrypted Linux package); `patch_tests` turns compiling off to stay engine-free.
- **The keys file** (`Keys.cpp`, `keys.file` or `KAGEX_KEYS_FILE`): every key a build uses, a key of its own for each kind of protection, in one text file kept outside the game's folder: `archive: <64 hex>` (xp3crypt), `scenes: <64 hex>` (scnfile) and the signing key's RSA private key PEM block (sigcheck; krkrsign reads the PEM out of the file as it is). `loadKeys` reads the keys `keysNeeded` says the settings use (`archive.encrypt`, `scenes.compile` + `scenes.encrypt`, `signing.enabled`) and refuses a missing one or archive == scenes; `validate` also refuses the file inside `data/` and warns inside the game's folder, and warns about the pre-0.9.0 fields (`archive.keyFile`, `scenes.keyFile`, `signing.privateKey`). `makeKeys` (`--cli keygen <file>`, `/api/release/keygen`, *Create keys…*) writes all three (random keys from libtomcrypt's `rng_get_bytes`, mode 600), adds the ones an existing file lacks, and replaces them only with `--force`. `Build` loads the keys once, up front. The order of a build: `stage`, `layered`, `media`, `scenes`, `signStage`, `scripts`, `fileList`, the patch, then `packArchives` (below); per platform the engine files, `archiveKeyInto`, `scenesInto`, binding, then signing. `test/smoke.py --tests keys` covers the file and its checks without engines.
- **A game's own plugins** (`gamePlugins` in `Project.cpp`): the libraries in `plugins/windows`, `plugins/linux` (Steam's too) and `plugins/macos` next to `data/` (`isPluginFor`: `.dll`, `lib*.so`, `.dylib`) are copied into the package after the engine's (`gamePluginsInto`: `plugin/`, or the app's `Contents/MacOS`), whatever `contents.plugins` says; the plan lists them and `validate` warns about other files there and about `plugins/web|android|ios` for an enabled platform (those engines link plugins in). Meant for krkrlive2d (`build.py --out plugins/<platform>`), which no engine package may carry. `test/smoke.py`'s `own_plugin_tests` (group `plugins`, and with `build`) uses dummy files (a real dylib on macOS, for codesign); a Linux package of the sample with the real plugin and Hiyori passed `smoketest.py --packaged --live2d required` here.
- **Test run.** The host's build runs with `-datapath` and `-replfile` in `.work/test` and `SDL_AUDIO_DRIVER=dummy` (plus `SDL_VIDEO_DRIVER=offscreen` on Linux without a display); the REPL is asked whether `kag` exists, then it runs 5 more seconds; script errors are read from `krkr.console.log` (UTF-16LE; outside Windows the engine names it `\krkr.console.log`, appending a backslash to the folder, so the engine's output is read there). A missing GLES context ("GLES context is unavailable", a VM) makes it inconclusive, not failed.
- **CI.** `.github/workflows/release-tool.yml` builds the tool (and kagex-lipsync, whose `tools/lipsync/test/smoke.py` it runs too) on Windows, Linux (glibc 2.34+, libstdc++ linked in) and macOS (arm64, 12.0+) and runs `tools/release/test/smoke.py` (`--browser` on Linux: the screen in Chromium, light and dark; `--engines`: builds of every platform the runner can make, including the web in Chromium through smoketest.py's `WebEngine`, an APK and an app bundle, iOS for the Simulator (started there) and a device `.ipa` signed ad hoc). The engine packages come from the newest release that has `kagex_engine_linux.zip` (looked up as `smoke.yml` looks up its engine); a tool newer than its engines only notes it. The scripts that make them run in the release workflow (its `tool-check` job builds the sample with the new packages before publishing) and in `platforms.yml`'s Android and iOS jobs, not here. The Windows runner gets GLES from Edge's ANGLE in PATH. Results go to `ci/platform-results-release-tool-<os>[-<branch>]`; the Linux job also pushes its vcpkg libraries and clipparse's sqlite source to `ci/dev-libs-linux` (in this environment vcpkg's GitHub archive downloads and sqlite.org are refused, and artifact downloads go through blob storage that is refused too). To build the tool here: clone `wamsoft/krkrz_tools` at the commit `ENGINE_SHA` pins (with submodules), unpack that branch's `x64-linux.tar.gz`, and configure without vcpkg's toolchain: `cmake -S tools/release -B <dir> -G Ninja -DCMAKE_BUILD_TYPE=Release -DKRKRZ_TOOLS_DIR=<krkrz_tools> -DCMAKE_PREFIX_PATH=<libs>/vcpkg_installed/x64-linux -DFETCHCONTENT_SOURCE_DIR_SQLITE3_AMALG=<libs>/_deps/sqlite3_amalg-src -DFETCHCONTENT_FULLY_DISCONNECTED=ON -DCMAKE_POLICY_VERSION_MINIMUM=3.5`. For `--engines`, a folder `kagex_engine_linux/` with the repo root's `krkrz`, `libSDL3.so.0`, `plugin/` and an `engine.json` (`{"format": 1, "platform": "linux", "version": "<tool version>", "debug": false}`) will do.
- **Versions.** The tool downloads its engines from the release tagged with its own version, `project(kagex_release VERSION ...)` in `tools/release/CMakeLists.txt` (also `version` in `tools/release/vcpkg.json`), so a release raises both along with the other version numbers (`first.ks`, `app-config.json`'s `versionName`/`versionCode`, `ios-config.json`'s `version`/`build`, `linux-config.json`, `CHANGELOG.md`). A release with a new feature raises the minor version (0.13.4 to 0.14.0), one with only fixes the patch (0.13.3 to 0.13.4); `versionCode` and `build` are minor × 100 + patch (1304, 1400). A forgotten bump would make the new release's tool download the previous release's engines, so the release workflow (`.github/workflows/release.yml` on branch `ci/windows-release`, pushed to start a release) stops in `tool-check` unless `kagex-release --version` prints `kagex-release <RELEASE_TAG>` (since 0.3.1). The release runs the `platforms.yml` on `ci/windows-release`, a copy of the release commit's: copy it there with every release that changes it (0.18.0 to 0.20.0 ran with 0.14.0's, and 0.21.0's first release run built Android without the Back patch).

## kagex-lipsync (tools/lipsync)

`kagex-lipsync` makes lip tracks (`<voice>.lip`) for the voices a game picks (`tools/lipsync/README.md`), so their characters' mouths show the vowels. Like kagex-release it's an appserve app (`web/`, embedded) and a CLI (`--cli list|make|check|align`). `tools/release/CMakeLists.txt` builds it: kagex-release is now `kagex_release_core` (everything but `main.cpp`) plus `main.cpp`, and `tools/lipsync` is added with the binary dir `lipsync-build` (`lipsync/` beside the exe is the tool's data folder), into the same output folder with `lipsync/`: PocketSphinx's `en-us` model and `cmudict-en-us.dict`, OpenJTalk's NAIST-jdic compiled at build time by MeCab's `mecab-dict-index` (103 MB), and their licenses; `KAGEX_LIPSYNC_DATA` overrides. PocketSphinx and OpenJTalk come by FetchContent at pinned commits (`FETCHCONTENT_SOURCE_DIR_KAGEX_POCKETSPHINX`/`_KAGEX_OPENJTALK` for local checkouts): PocketSphinx's own CMakeLists.txt only works as the top project (`CMAKE_SOURCE_DIR`), so its library is built from the source list in its `src/CMakeLists.txt`; OpenJTalk's works as a sub-project (it writes `mecab/src/config.h` into its source, and its include directories aren't on the target).

- **Aligning** (`Align.cpp`): the voice is decoded (krt_audio, with an Opus header gain applied; FLAC through dr_flac, which the core's `Media.cpp` implements), averaged to mono and resampled to 16 kHz (windowed sinc). A line with kana or kanji is Japanese: OpenJTalk's front end (text2mecab, MeCab, NJD, JPCommon labels: the phoneme between `-` and `+`) gives its phonemes, mapped to the nearest ARPAbet sounds (`kJapaneseSounds`; `cl` dropped), a word per stretch between `pau`s, added with `ps_add_word`. English words are looked up in CMUdict (lower case; one it lacks is left out, with a warning). PocketSphinx aligns the words (`ps_set_align_text`), then the phones (`ps_set_alignment(ps, NULL)`, a second pass), as `pocketsphinx align -phone_align yes` does. Each phone's mouth (`kEnglishMouths`, a diphthong as two halves; `kJapaneseMouths`), how open from the RMS at the native rate (0.03/0.12), the later of two marks at one time. A voice that doesn't fit its line fails in the phone pass ("type what it says"): Pip's babble, and Ai's recording against its translated line. Paths reach the C libraries as Windows short names (`narrowPath`). Measured (scratch, not in the repository) on Kokoro lines in 4 Japanese and 4 English voices with the phoneme timings as the truth: vowel right 86%/87%, vowel shown 69%/75%, open/shut 79%/82% (a perfect track: 90%, 78-82%, 86%). Julius with the segmentation kit's Japanese model did 3 points better at vowel shown in Japanese but has no CMake build; Rhubarb 61% (English) and 23% (Japanese, phonetic); getVowel 22%/39%.
- **Lines** (`Voices.cpp`): the framework's `-voicelines=<file>` (`Initialize.tjs` `KAGListVoiceLines`, `KAGEnvPlayer.voiceLines`: each script `SceneParser.compile`d without writing, `env.extractVoice` resolves the voices' files, the texts that carry a message on (`TEXTFLAG_CONT`) joined, `readingText` puts a ruby's reading in place of the character under it), run with the engine next to `data/` or this computer's engine package (`findGameEngine`: kagex-release's `ensureEngine`; on macOS a copy signed ad hoc, in the cache), headless (the window stays hidden, `MainWindow.tjs`), `-datapath` in the cache; it writes `<file>.out` (UTF-16; `voice\tcharacter\tscript\ttext\treading\tlanguage`: with more than one language a line per language, the source language first, from the compiled texts' per-language entries through `convertSceneText`/`scnTextIn`). `makeTracks` aligns a voice to the first of `lineTextsFor` (the distinct readings, in that order) that fits it, so Ai's Japanese recording gets its track from the Japanese line (the lipsync smoke test checks it on a copy of the sample). Only scripts that can voice a line are listed (`mayHaveVoices`: `【` in UTF-8, Shift_JIS or UTF-16LE, or `voice=`): system scripts with `[call]`/`[return]` don't compile. Voices are matched to files by bare name across `data/` (not `data/system`); every sound in a folder named `voice` is listed too.
- **State**: the `.lip`'s header (`# kagex-lipsync <version>`, `# voice: <SHA-256>`, `# text:`, `# language:`) makes it none, current, stale, manual (no header) or missing; `LipTracks.cpp` in the release core reads it, and kagex-release's `validate` warns about stale tracks (hashes cached by size and time: the window checks often). A track is written by replacing the file.
- **Tests**: `tools/lipsync/test/smoke.py` (release-tool.yml, every OS): `align` of `pip000009.ogg` and `test/ja_sample.ogg` (Kokoro `jf_alpha`) against the committed tracks (vowels in the same order, 85% alike), the babble refused, `make --text` then `check` (current, then stale once the voice changes, and kagex-release's warning), and with `--engines` `list` of the sample (pip000009's line and state, ai000001's lines in English then Japanese) and `make` of ai000001 on a copy of the sample (made from the Japanese line). The artifact `kagex-release-<os>` carries both tools and `lipsync/`.

## Conventions and gotchas

- **Two `Config.tjs` files.** `data/main/Config.tjs` is the one in effect (it shadows `template/system/Config.tjs`). Recent commits keep both in sync for settings like `scWidth`/`scHeight` (currently 1920x1080); do the same. Setting lines use the `;name = value;` form, and the `//[start-...-additionals]` / `//[end-...]` markers must stay — `UpdateConfig.tjs` parses both when migrating configs. The `KAGWindow_config` etc. functions run `incontextof` the target object, so settings like `scWidth` become **members of `kag`**, not globals.
- **Plugin linking.** Plugins are linked by explicit relative path with a `.dll` name on every platform — `Plugins.link("plugin/foo.dll")` — wrapped in `try {} catch {}` and, where possible, guarded by a `typeof` check on a symbol the plugin provides (avoids double-loading on case-sensitive Linux, and tolerates plugins the SDL3 build provides natively or lacks). `Initialize.tjs` does this through `KAGLinkPlugin(name)`, which logs a failure to the console instead of swallowing it. Follow this pattern; bare `Plugins.link("foo.dll")` was deliberately removed in `0710553` (the x64 Windows engine's own plugin folder is `plugin64/`). On non-Windows engines (`System.platformTag` present and not `"windows"`), the top of `Initialize.tjs` wraps `Plugins.link` to drop the `plugin/` prefix, because the SDL engine turns `plugin/Foo.dll` into `libplugin/Foo.so`; its own search already finds `plugin/libFoo.so`.
- **Linux compatibility.** Storage names in scripts must match file case exactly, and use `/` separators. Plugin names too: the packages ship `libsaveStruct.so`, so `Plugins.link("plugin/savestruct.dll")` only worked on Windows. That includes data files such as `musiclist.csv` (it listed `BGM01` for `bgm01.ogg`, which played on Windows only).
- **SDL3 port patches.** The end of `Initialize.tjs` re-applies the window size with `kag.setZoom(kag.zoomNumer, kag.zoomDenom)` unless full-screen, so a windowed start keeps the zoom the constructor picked for a display smaller than 1920x1080 (it used to force `setInnerSize(scWidth, scHeight)`). Both `Config.tjs` files shadow `getInitialFullScreenState`: full-screen on the first launch, then the saved `scflags.fullScreen`. The SDL engine switches full screen asynchronously, so `kag.fullScreen` (which reads the window back) still reports the old mode right after a switch: `changeFullScreenOrWindow` records the requested mode in `kag.fullScreened`, and anything deciding by the current mode (the Config screen's buttons, the size at the end of `Initialize.tjs`, the saved preference) should read `fullScreened`. Be careful reordering anything around window creation and `kag.process("first.ks")`. The SDL engine's `Window` has no `menu`: `KAGWindow_createMenus` (`Menus.tjs`, and the sample's copy in `Override.tjs`) builds the menu items on the stand-in `Menu` class `Menus.tjs` defines, and the framework's version marks that with `kag.menuBarStandIn`; without it a game made from the template stopped at start-up (`Member "menu" does not exist`). Those items show as a menu bar above the game in a window (`MenuBar.tjs`: The interface, below), and KAG's debug mode (`debugWindowEnabled`: on unless `-debugwin=no`, which a release should set) also gets Shift+F12 (debug window) and Shift+F11 (debug level) as key bindings (`createKeyBindings`). The sample's `KAGWindow_createMenus` copy sets `menuBarStandIn` too. The SDL engine has no `Pad` class either: `initLogPad` returns early and `UpdateConfig.tjs` writes `Config.tjs.merged` instead of showing a Pad. `MainWindow.tjs` only takes its windowEx path (extended events, menu-bar hiding, registry cursors) when both `registerExEvent` and `exSystemMenu` exist. Newer engines build `registerExEvent` in on every platform, while `exSystemMenu` only comes from the windowEx plugin. Likewise `Window.minimize` is built in, but the `MenuItem.bi*` icons are windowEx's, so `SetWindowControlMenu` (`Menus.tjs`) returns early without them; it used to throw `Member "biMinimize" does not exist` on every switch between full screen and a window, which skipped the rest of the `fullScreen` setter (the `afterChangeScreenMode` hook, the menu-bar update).
- **File encoding.** Most scripts are UTF-8 **with BOM**, but not all (e.g. `template/system/Config.tjs` has none); line endings and a doubled-blank-line artifact (left over from a CRLF conversion) vary by file. Preserve whatever the file already uses and keep diffs minimal — do not normalize whitespace, strip BOMs, or collapse the blank lines as a drive-by. `◆`/`●` markers and some Japanese comments are intentional.
- **The sample's images are generated** by `tools/assets/` (README there): `make_ui.py` draws everything in `data/image` plus `template/system/LineBreak*`/`PageBreak*`, `fgimage/star.png` and `thum_replay_char` in one theme (the Yes/No dialog's: lavender panel (166,144,255), violet (80,37,255) borders and hard shadows, white buttons that go violet when hovered or selected, white labels with a navy (1,0,98) outline, light dotted screen backgrounds), with labels from the Noto Sans CJK JP subsets in `tools/assets/fonts`. `make_ui.py preview` crops `title.png` to the web build's 1200x630 link-preview image (`platform/web/preview.jpg`). `upscale.py` rebuilds `fgimage/ch_*`, `bg01_01`, `event1` and `thum_event1` from the original art in `tools/assets/src` with Real-ESRGAN in NumPy (anime model for sprites, x4plus for the photos; 4x, then down to 1.8x, or 2.4x and the middle 1080 lines). `make_effects.py` makes `data/effect` (see the Effekseer note below), `make_rules.py` the transitions' rule images in `data/rule` (see the transitions note), `make_vector.py` the layer demo's SVG emblem and its PNG twin in `data/fgimage`, `make_clip.py` the same emblem as `emblem.clip` (needs the engine), `make_pip.py` the Animated Character demo's Pip (`data/fgimage/pip`, `charinit.csv`, `charanim.csv`, and with `voice` its babble lines `data/voice/pip*.ogg`, through ffmpeg's libvorbis; with `speech` its one line in a synthesized voice, `pip000009.ogg`, through Kokoro in ONNX Runtime, whose `.lip` kagex-lipsync makes), `make_opening.py` the logo's opening movie (`data/video/opening.webm`, `opening_sd.webm`) and its Replay tile, `psdwrite.py` (standard library only) writes a layer structure and its pictures as a PSD with folders, for tests. Change the scripts and rerun them instead of editing the PNGs; `title.png` and `thum_replay_char` are drawn from the upscaled `bg01_01` and `ch_0_0_1`, so run `upscale.py` first. A panel's hard shadow (`Canvas.panel`) is drawn only outside the panel, so translucent panels (the message window, the choices) stay evenly see-through; anything drawn inside a rounded panel has to stay inside its border's rounded inner edge (the message window's top highlight is clipped to it).
- UI coordinates in `.ks` files (`title.ks`, `config.ks`, …) and the images in `data/image/` are authored for a specific resolution; a resolution change means touching both. The screens share a grid: content from x 290 to 1630, a header title at 290 with a rule at y 170, and 180x64 nav buttons (`return`, the Extras tabs, `config_title`/`config_initial`) right-aligned at y 78. `title.ks`/`title.png`, `config.ks` (with its `config_*` and `slidebar*` images; two columns of six 130-high rows from y 206, the left one ending with Language) and the extras screens `cgmode.ks`/`replay.ks`/`musicmode.ks` (`*mode_base`, `extra_*`, `cgmode_page*`, `cgmode_thum_*`, `musicmode_*`, `track*`) and `save.ks`/`load.ks` (`save_base`/`load_base` (semi-transparent so the scene shows through), `sl_win_base`, `*_win_over`, `page1-9`, `newdata`; save thumbnails are 234 wide via `thumbnailWidth` in `data/main/Config.tjs`, and `fileDataButton` in `Override.tjs` lays out the slot: it draws the thumbnail, badge and text into each of the button's three states, so `sl_win_base` is the normal look and `save_win_over`/`load_win_over` the hovered one) are at 1920x1080, as is the choice menu that opens on START (`[selopt]` in `first.ks` sets its area and `size=36`; bars are `select_normal`/`select_over`, and `SelectLayer` spaces the choices evenly within the area). The demo scenes are 1920x1080 too:
  - Art: `bg01_01` and `event1` are 2.4x the 800x600 originals, trimmed to 16:9; character sprites (`fgimage/ch_*`) are 1.8x (`upscale.py`). `black`/`white` are 1920x1080. The name has no brackets: the sample's `dispNameFilter` is gone, and `MyHistoryLayer.storeName` brackets it in the history. The sample `Config.tjs` text is 39 (line spacing 5, ruby 15/-3).
  - World (`envinit.tjs`): `yoffset` and vertical motion are x1.8. Horizontal positions and moves are x2.4, so `posleft`/`outleft` etc. sit at the same fractions of the wider screen.
  - Hardcoded scenario offsets (`layer.ks` character/rotation origin, `char.ks` walk-off, `envlayer.ks` star paths) were scaled the same way.

- **Shrink whole pictures with `KAGShrinkCopy`** (`Utils.tjs`), not `Layer.shrinkCopy`: the plugin reads a row past the bottom of the source for its last pixel (rounding in its weights), which crashed Android's game as it saved a thumbnail (`UPSTREAM.md` 39); it reads the column right of the last one too (in memory the next row's first pixel), so the helper shrinks from a copy with a column more on its right and two rows more under it, edges repeated, starting at 0, 0 (a source rectangle that doesn't start there comes out differently at the plugin's edges); one extra row wasn't enough (0.17.0's Live2D run crashed with it). - **Never test a string as a boolean** (`if (s)`, `s ? a : b`). The current engine converts it to a number, so `"event1"` is false, and an empty string segfaults it (`tTJSVariantString::ToInteger`). Compare instead: `if (s != "")`. This crashed the Replay screen whenever an unlocked entry had no thumbnail.
- **Font faces on the SDL engine.** A face name the engine has not registered (e.g. `MS Gothic` on Linux, and on some machines plain `Noto Sans CJK JP` when only the Light weight is registered) is drawn with its `elements_basic` icon font, so text shows as `←←←`. The engine's own default face (an empty face) has the same problem here. So `userFace` and the history `fontName` in both `Config.tjs` files, plus the explicit faces in `about.ks`, `Override.tjs` and the history classes' defaults, are face lists with Yu Gothic first: `"Yu Gothic Medium,Yu Gothic,Noto Sans JP,Roboto"` (the template uses the same list). **Noto Sans JP ships in `template/system/notosansjp-regular.otf`** (the engine's own `resource/notosansjp-regular.otf`, SIL OFL, `notosansjp-OFL.txt`): since engine 2.5.0 the engine embeds only Roboto, so Japanese depended on system fonts and drew as U+FFFD boxes without them. `Initialize.tjs` registers it with `Font.registerFontFile(path, "Noto Sans JP")` after the plugins, which records the name without opening the file; `Font.getVarAxes` then resolves it and krkr_richtext draws it. Where the engine already has a font of that name (the browser build bundles Noto Sans JP in its `resource/`), it loads the file with `Font.addFont` instead: the engine finds a bundled font only in the exact style asked for, and its rasterizer keeps one face chain, rebuilt only when the first face of the list changes, so the first text drawn in a face list being bold (the `[select]` choices) left that chain on the icon font (`elements_basic`, which its fallback means to skip): every text came out as arrows measuring 0 wide. A loaded font is found in any style. To check rendering without system fonts, run with `FONTCONFIG_FILE` pointing at a config whose only `<dir>` is empty. Up to 0.0.4 the list was `"Yu Gothic Medium,Yu Gothic,MS Gothic,Noto Sans CJK JP,Noto Sans CJK JP DemiLight,Noto Sans CJK JP Light,Roboto"`, which is now in `previousDefaultFaces`; the notes below about system Noto CJK names explain why that list looked like that. Unknown names in a list are skipped, and both the engine and krkr_richtext pick a font per character from the list. Yu Gothic leads on Windows because its Latin letters are proportional and kerned: MS Gothic's are fixed-width, which made English look gappy (`over lap`) and left krkr_richtext nothing to kern. Yu Gothic Medium is the readable weight on screen; plain Yu Gothic is the fallback where Medium is missing. Don't pick a font that isn't the first in its `.ttc` (MS PGothic, MS UI Gothic, Yu Gothic UI, MS PMincho): the engine's `drawText` gets those right, but krkr_richtext draws the collection's first font instead (MS Gothic, Yu Gothic, MS Mincho), so MS PGothic comes out monospaced again. That's an upstream bug (plugin or engine), seen on Windows; the template used `MS PMincho` until 0.0.4 and was affected. Plain `Noto Sans CJK JP` fails on Arch because the Light file also claims the Regular style, while the weight-suffixed names resolve. Roboto ships with the engine, so it is always available for Latin text. `kag.chDefaultFace` is saved into the system variables (`*sc.ksd`, `scflags`) and wins over `Config.tjs`. When a saved value is a single old-style name (e.g. `MS Gothic`), the restore code in `MainWindow.tjs` keeps it first and appends the configured list. A saved value equal to a default some earlier release shipped (`previousDefaultFaces` in `MainWindow.tjs`, which now lists `ＭＳ ゴシック`, `MS Gothic`, the 0.0.2 list and the template's old values) is replaced by the configured default instead, so a changed default reaches existing saves; add the old value there whenever a default changes. Without `-datapath` the engine keeps that data in `~/.local/share/wamsoft/krkrz/`, not `savedata/`. Use the face lists for any new text too.
- **krkr_richtext.** With `useRichText` (MessageLayer_config, on in both `Config.tjs` files) and the plugin loaded, `drawTextToLayer` in `MessageLayer.tjs` draws message text, ruby and the name box through `RichTextFontApp`: vector edges/shadows built from the layer's edge/shadow settings, fake bold, and in `processCh` kerned advances (the exact width of the line's run, rounded per character). **A line's characters drawn together** (`useStyledLayout`, both `Config.tjs` files, since 0.12.1; `drawStyledRun`): each `processCh` adds its character to the run (`styledRun`: one style and app key on one line, from `startStyledRun`, which copies what the line layer has from the run's start into `styledRunBack` and keeps the style, baseline and a `clone()` of the appearance), and `flushStyledRun` lays the run out with `RichText.StyledLayout` (escaped markup, `default` style and app, 100000 wide so it never breaks), copies back what was under it and draws it whole at the baseline (`y + baseLine + Layout ascent`). The flush runs from an `AsyncTrigger` (`styledRunTrigger`, once the conductor stops: drawing the run again for every character made a page of instant text take a second) and before anything else uses the line layer (`fixLineLayer`, `changeLineSize`, `putGraph`, a new run); `initLineLayer` drops the run. The advance is `RichTextFontApp.advance`'s, as before, so every character's `x` is what it was (checked: the same `x` for every character, the Japanese line pixel for pixel, a page of instant text as fast). So accents, emoji and other sequences of several UTF-16 units come out shaped (the old path drew a combining accent apart and a surrogate pair as two boxes). A character with ruby is a run of its own (`alone`, drawn at once) and keeps KAG's ruby (StyledLayout's is half size and can't be moved: `UPSTREAM.md`); a pitch, `hasChFadeLayer`, vertical text and bitmap fonts draw a character at a time. krkr_richtext's raw-callback layer methods (`drawStyledLayout`, `drawTextLayout`, `drawStyledText`, ...) skip ncbind's instance hook, which finds the layer's pixels (`reset()`): as the first drawing on a layer `drawStyledLayout` threw "wrong context" (実行コンテキストが違います), and after a `copyRect` into the layer it drew where the pixels had been (the run came out one character behind), so `flushStyledRun` reads `ll.useCache` before every draw. A test that reads the line layer right after `processCh` calls `flushStyledRun()` first. Vertical text and bitmap fonts keep the normal path, as does anything when the plugin or the fonts are missing. The `[select]` choices and the history log (both `data/main/MyHistoryLayer.tjs` and `template/system/HistoryLayer.tjs`) follow the message layers' `useRichText` with `RichTextFontApp` instances of their own: `SelectLayer` puts its app into the style dictionary as `richTextApp`, and the history draws whole lines through `drawHistoryText` (no edge or shadow, as before). `SelectLayer` borrows `MessageLayer.drawTextToLayer` `incontextof` that style dictionary, so that function may only touch members the dictionary has (a call to a MessageLayer method there broke every `[select]`). Text widths must come from the path that draws the text, or English lines break in the middle of a word once the font is proportional: `MessageLayer.measureText`, `SelectLayer.measureText` (choice centering) and `HistoryLayer.textWidth` (wrapping, action marks, indent) measure with krkr_richtext when it draws, and the word wrap in `MainWindow.tjs` (`needsToBeWrapped`) measures words through `msgTextWidth`/`histTextWidth`. Edges and shadows: `Layer.drawText` draws both as a blurred copy of the glyphs. The edge becomes a stroke reaching `edgeExtent` past the glyphs, fully opaque from `edgeEmphasis` 255 up (the default 512) and fainter below; a shadow with `shadowWidth` (blur) > 0 gets three widening translucent strokes around the offset copy. The sample's settings (shadow, offset 2, no blur) render the same either way. The baseline comes from the engine's `getGlyphDrawRect("H")`, so lines sit where `drawText` put them. The line layer only reaches `lineLayerPadding` (4) below the text cell, and krkr_richtext's descenders (g, y) plus the shadow reach further, so they were cut off at the bottom of each line: `MessageLayer.updateLineLayerPadding` (from `initLineLayer`) widens the padding per line from `RichTextFontApp.bottomOverhang`, and without krkr_richtext (the browser and iOS builds) from the engine's `getGlyphDrawRect("gjpqy")` plus the shadow or edge, where the 4 px cut 2 px off every descender; it's symmetric and every offset uses it, so nothing moves. `drawTextEx` only calls `update()` on the glyphs' ink box, which leaves shadows and edges off the screen until something else repaints there (text looked clipped while typing, then changed when the line was committed), so `RichTextFontApp.drawText` updates the whole padded cell itself. **Never pass `RichText.registerFont` (or `Font.getFontInfo`/`Font.queryFonts`) a face name the engine can't resolve:** the engine then opens every system font to search their names, and its pooled file allocator deadlocks (it runs the storage-cache pressure callback while holding its own mutex, at 75% of `-filepoolsize`, default 256 MB). A hung engine ignores SIGTERM; use `kill -9`. `RichTextFontApp.getFonts` only registers names that `Font.getVarAxes` resolves (it uses the same lookup as `drawText`, without the search) and that the engine actually draws; plain `Noto Sans CJK JP` passes the first test on Arch but draws nothing, so the chain here is DemiLight → Light → Roboto.
- **Engine BMP bug.** The current engine's BMP writer puts `bfOffBits = 56` in the header but writes the pixels at byte 54, and its reader trusts the header. The cause is in the engine's `common/visual/GraphicsLoaderIntf.h`: `#pragma pack(push, 1)` around `TVP_WIN_BITMAPFILEHEADER` is only applied under `_WIN32`, so on Linux (and macOS) the 14-byte header struct is padded to 16 and `sizeof` gives 56; Windows builds write correct BMPs. Don't patch the engine (krkrz_dev is off-limits). So anything saved with `saveLayerImage(..., "bmp")` comes back color-shifted. This is a krkrz bug. To avoid it, bookmarks (`MainWindow.tjs`) now save their thumbnail as PNG: the save files are `dataN.png`, the save data starts at `calcThumbnailSize().size` (sized for an uncompressed RGBA PNG), and the thumbnail is forced opaque because PNG keeps the snapshot's meaningless alpha. `thumbnailDepth` is unused, and old `.bmp` saves are no longer picked up (only 0.0.1, the 800x600 Windows package, wrote them: PNG thumbnails came in 0.0.2). The engine picks image decoders by file extension, so PNG data in a `.bmp`-named file won't load. The PNG is shorter than that offset, and seeking past the end of a file fails on some storage ("Seek error" in the browser), so `saveThumbnailAndData` (used by `saveBookMarkToFile` and `rewriteBookMarkToFile`) grows the file to the offset with `Storages.truncateFile` first. Where the save folder isn't a local file (`user://` in the browser, Android and iOS builds), `truncateFile` throws "Cannot get local name": the file is then put together in `Storages.getTemporaryName()` (a native path, made a storage name by `localStorageName`) and copied over with `Storages.copyFile`. Before this, every save there failed and showed the save-failed message, which blocked the title screen's anchor save.
- **REPL results.** The file channel pretty-prints a command's result on its own thread, racing the main thread's TJS reference counts (`UPSTREAM.md`): an engine driven through it aborted now and then ("double free or corruption", 0xC0000374), about one run in five of the release smoke test on the runners and mostly in the busy Animated Character demo, never locally. So `run-kagex.ps1`'s `Invoke-Tjs` and `smoketest.py`'s `FileChannel.tjs` wrap every command so that the main thread writes the value to `result.txt` in the channel folder (`Array.save`: UTF-16 with a BOM; the command's number as `#<n>`, then a type letter `S`, `N`, `V` or `O` and the value) and the REPL only returns 0. Do the same in any new harness, and write the file over rather than deleting it first: the engine rebuilds its whole auto path table whenever a script makes a new file ("自動検索パステーブルを再構築しています", 5-7 ms for the sample's 900 files), so up to 0.26.0, when both harnesses deleted it before each command, every poll of every wait cost the game that, and a command took 56 ms instead of 51; the number tells this command's result from the last one's. `run-kagex.ps1` defines its writer once (`__ciSave`, again when the error names it), as `smoketest.py` does its runner: the engine keeps every block it compiles that has a function in it. The other targets' REPLs (the web's `krkrz_repl_eval`, Android's socket, iOS's `/pad/exec`) return the pretty-printed value, where a string is a TJS literal (`EscapeC`: an apostrophe comes back as `\'`, which JSON refuses; the web build's language step failed on "It's" in 0.10.0's first release run), so `Engine.tjs` has the game return a string as the hex of its UTF-16 code units (`S:` and four digits a unit) and decodes it. It was found by running the release smoke plan on the runners under gdb (probe branches since deleted; earlier probes blamed the general memory pool, whose `-krkrzpoolsize=none` only made the aborts rarer).
