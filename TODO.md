# To do

Planned features, in three groups. The first two need only work in this repository (scripts, data and kagex-release): the plugins and engine features they use are already in krkrz_dev's default build and ship in the Linux package, and krkrz_dev itself isn't changed (`CLAUDE.md`). The third needs changes to the builds as well. The last section lists the plugins looked at and left out, and why.

## From krkrz_dev: plugins and engine features

- [ ] **Characters straight from PSD files** (`psdfile`): a character drawn from layers reads each pose's layers from psdlayer.tjs's text format, with a picture per layer (what `tools/assets/make_pip.py` writes for Pip). psdlayer.tjs can also read a `.psd` itself (`PSDInfo.loadPSD`, with psdfile's `PSD.getLayerData` rather than `psd://`, whose BMPs don't load outside Windows), so `StandPSDInfo` could take `<files>.psd` when there's no `.txt`, and artists could keep editing the PSD. Only the desktop builds have psdfile: either kagex-release writes the text format and pictures from the PSDs at build time (psdlayer.tjs's `saveImages` does it, but in the engine, with layerExSave and saveStruct), or the web, Android and iOS builds gain the plugin. kagex-release leaves `.psd` files out unless a script names them after `psd://`, so it would also keep the ones `charinit.csv` names. psdfile writes PSDs but can't make folders, so testing this needs a PSD writer of our own.
- [ ] **Mouths by vowel**: the engine's `WaveSoundBuffer.getVowel` estimates how much the voice sounds like a, i, u, e and o, so a face could have a mouth for each vowel instead of three openings. No plugin needed.

## Needing more than scripts

These change the builds too: native code for every platform, including the web, Android and iOS engines in kagex-release's engine packages (the web build links its plugins into `krkrz.wasm`).

- [ ] **Live2D** (`krkrlive2d`): krkrz_dev has the plugin (`Live2DDevice`, `Live2DModel`, `Live2DPlayer`, `Live2DMatrix`), but builds it only with the Live2D Cubism SDK (the `CUBISM_SDK` environment variable), so the release workflow and `platforms.yml` would need the SDK, which Live2D distributes under its own license rather than as open source. Releasing a game with it can need Live2D's SDK release license, which the documentation should say. Then a World character whose poses and faces are motions and expressions, blinking by itself and lip-syncing to its voice as characters drawn from layers do (`WaveSoundBuffer.getSoundLevel`). `Live2DDevice` can take the engine's own OpenGL draw device (`OGLDrawDevice`), so it doesn't need `krkrgles`.
- [ ] **3D scenes and VRM characters** (`krkrthreepp`): threepp, a C++ port of three.js (scenes, cameras, lights, materials, glTF), and VRM avatars (VRoid and the like, 0.x and 1.0) with expressions, eye direction, VRMA animations, spring bones and MToon toon shading. It draws through the engine's `GLCompositor`, as krkreffekseer does, and the Windows, Linux and macOS packages already ship it. A `3d` flip type would render a scene into a layer, as `efk` plays effects; then World characters as VRM avatars, with faces as expressions, poses as VRMA animations and lip-sync through `WaveSoundBuffer.getSoundLevel`. The sample can't include a VRM model (no third-party art), so it would show a 3D scene built in script, and a game brings its own model. The plugin's presets include Android but not iOS or the web, and iOS may hit the same Xcode error as krkreffekseer.
- [ ] **Compiled scenarios** ([krkren/scnfile](https://github.com/krkren/scnfile)): kagex-release compiles the `.ks` scripts in `!scnlist.txt` into encrypted `.scn` files that a plugin of our own (`SCNFile`) reads, and the scene player in `KAGEnvPlayer.tjs` (`[scenestart]`, the World's `playerExecMode`) plays them. That gives scripts out of plain view, jumping to any line, rollback, read tracking per line and dialogue search, all of which the player already has. Milestones 1 to 3 are done: `SceneParser.tjs` compiles the listed scripts, the sample plays its demos compiled (`doc/scn.txt`), the scnfile plugin reads and writes them as `.scn` (PSB) on Linux, falling back to `.scn.json` where a build lacks it, and kagex-release compiles a game's scripts, encrypts the `.scn` files with the game's key, writes the key into each package's plugin and leaves the scripts out. Milestone 5 is done too: BACK and the backlog's marks go back (with KAG's own state for the last 100 clicks), Replay has a tile for every titled scene, and Search finds the lines read and plays from one (`doc/scn.txt`). Next: the plugin in every platform's engine (the release workflow building scnfile into the zips and the engine packages, and linking it into the web, Android and iOS engines; until then kagex-release with the released engines compiles to `.scn.json`), and CI for scnfile and for kagex-release's scenario tests. Going back to a click in the middle of a message window shows that click's text alone (as a load does): the page's earlier lines could be redrawn from the history. A compiled script starts from an empty World; one that carries on from another script's screen needs the compiler to follow where it's reached from (the player's `depend` methods). scnfile reads and decrypts `.scn` (PSB) files and nothing else; the archive (below) is encrypted separately. A patch to compiled scripts needs the compile step too, and recompiling can move save points (the root `hash` lets the player notice).
- [x] **Encrypted game files** ([xp3crypt](https://github.com/krkren/xp3crypt), a standalone plugin + library + CLI of its own, so other Kirikiri Z games can use it; not coupled to scnfile): kagex-release packs every file in `data.xp3` encrypted, and the plugin decrypts each one as the engine reads it, through the engine's XP3 extraction filter (`TVPSetXP3ArchiveExtractionFilter`; the engine at `21d20e9` still calls it for every read). The SDL engine doesn't auto-load `.tpm` plugins, so the plugin is linked into the engine (`TVP_PLUGINS_STATIC`), installing the filter at V2Link before `startup.tjs`. The cipher is XChaCha20 (Monocypher), keyed per file: each file's XChaCha20 key and nonce come from keyed BLAKE2b of the game key and a unique per-file number the packer writes into the file's `adlr` chunk (the engine doesn't verify adler32 on read, and an encrypted file's bytes wouldn't match a plaintext adler anyway), so no two files share a keystream. Files are stored uncompressed (the filter runs after the engine's zlib step, and ciphertext doesn't compress). The filter decrypts reads at any offset, which a stream cipher can seek to, but leaves no place for a whole-file tag, so tampering is caught by signing (below), not the cipher. The key ships in the game: kagex-release writes each game's key into a 16-byte-marker slot inside that game's engine (prebuilt engines can't have it compiled in), before signing (macOS, iOS) and before the web build's id, so breaking one kagex game doesn't open the others. With no key in the slot the filter passes reads through, so the same engine reads a plain archive. Turn it on with `archive.encrypt` + `archive.keyFile` (or `KAGEX_ARCHIVE_KEY`); `kagex-release --cli keygen <file>` makes a key. Done and verified on Linux (the plugin built statically into the engine; an encrypted, bound sample boots and reads its scripts). Left for later: the key is one block in the slot, not scattered through the binary, and the archive's file index stays readable (hiding it needs an archive of our own with an encrypted index). Not planned: a cxdec-style routine generated per game (obscurity, not strength; would mean a plugin per game per platform). The key still ships with the game, so a determined person gets in; this makes each game take real work.
  - **Engine builds**: the shipped engine packages must have xp3crypt built in. For a krkrz_dev build, pass `-DTVP_PLUGIN_FOLDERS=<xp3crypt>/plugins -DTVP_PLUGINS=xp3crypt -DTVP_PLUGINS_STATIC=xp3crypt` (these `list(APPEND ...)` onto the engine's own lists, so the other plugins still build). Still to wire into CI (`release.yml` zips, `platforms.yml` kits — the kits link their own plugin lists) and the engine-package scripts; CI must check out the private `krkren/xp3crypt` at a pinned commit. Web/Android/iOS are wired in kagex-release but only Linux is verified; the key goes into `krkrz.wasm` / the engine `.so` / the app binary, which needs checking per platform. **Combine-time snag:** if both scnfile and xp3crypt are linked statically into one engine, their separately vendored Monocypher symbols clash — share one copy when merging the features.
- [x] **Signed game files** (`sigcheck`, since 0.9.0): kagex-release signs the game archive (or the executable it's bound into), the engine and its plugins, the per-folder/part archives and each patch zip with the developer's RSA key (RSA-PSS/SHA-256, `<file>.sig`; the private key is kept out of the repository and is never stored in `release.json`). At start the game (`template/system/SignatureCheck.tjs`) checks them with `Window.checkSignature` and the public key written into `data.xp3`, and starts `first.ks` only when they all pass; otherwise it names the file and quits. `checkSignature` is a method of the game window, so no separate window is needed; the check is asynchronous, so start-up is gated on its completion and patches/extra archives mount only after the framework and `Config` load (they can change assets, not the framework). A self-test (a decoy with a mismatching signature) catches a stubbed plugin, and the build refuses REPL/startup options and debug mode. The SDL engine has none of the old Kirikiri executable markers, so sigcheck hashes each file whole; the engine files to check are listed in a signed `<exe>.sigfiles` beside the executable. The web, Android and iOS builds have no plugin, so they skip the check (signed by the platform / served from the developer's site). Done in this repository and kagex-release alone (the plugin and `krt::sig` were already in krkrz_dev); the open items are the plugin's 32-bit size limit and its repeated reads (`UPSTREAM.md`), worked around here by splitting archives under 2 GB. Compiled scripts and an encrypted archive (above) would make the in-archive check much harder to remove.

## Looked at, not planned

- `layerExAreaAverage`: shrinks by area averaging, which `shrinkCopy` already does, in half the time and without the glitches `stretchCopyAA` left in text.
- `layerExLongExposure`: averages frames into one image, an authoring tool for rule images, which `tools/assets/make_rules.py` makes.
- `lineParser`: `[].load()` already reads a file line by line, and the framework parses with KAGParserEx and csvParser.
- `expat`: XML parsing; nothing in kagex reads XML, and only the desktop builds have it.
- `krkrgles` (Windows only): an OpenGL ES context through ANGLE, for engines without one. The SDL engine draws with OpenGL ES, and krkreffekseer, krkrthreepp and krkrlive2d use its context.
