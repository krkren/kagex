# To do

Planned features, in three groups. The first two need only work in this repository (scripts, data and kagex-release): the plugins and engine features they use are already in krkrz_dev's default build and ship in the Linux package, and krkrz_dev itself isn't changed (`CLAUDE.md`). The third needs changes to the builds as well. The last section lists the plugins looked at and left out, and why.

## From krkrz_dev: plugins and engine features

- [ ] **Characters straight from PSD files** (`psdfile`): a character drawn from layers reads each pose's layers from psdlayer.tjs's text format, with a picture per layer (what `tools/assets/make_pip.py` writes for Pip). psdlayer.tjs can also read a `.psd` itself (`PSDInfo.loadPSD`, with psdfile's `PSD.getLayerData` rather than `psd://`, whose BMPs don't load outside Windows), so `StandPSDInfo` could take `<files>.psd` when there's no `.txt`, and artists could keep editing the PSD. Only the desktop builds have psdfile: either kagex-release writes the text format and pictures from the PSDs at build time (psdlayer.tjs's `saveImages` does it, but in the engine, with layerExSave and saveStruct), or the web, Android and iOS builds gain the plugin. kagex-release leaves `.psd` files out unless a script names them after `psd://`, so it would also keep the ones `charinit.csv` names. psdfile writes PSDs but can't make folders, so testing this needs a PSD writer of our own.
- [ ] **Mouths by vowel**: the engine's `WaveSoundBuffer.getVowel` estimates how much the voice sounds like a, i, u, e and o, so a face could have a mouth for each vowel instead of three openings. No plugin needed.

## Interface, accessibility and languages

- [ ] Screen readers: KAG has no support of its own, so the message window should pass its text to `ElementsDialog.announce`, and the choice menu should expose its choices with `ElementsDialog.setGameA11y` (engine guide: Accessibility).
- [ ] Japanese and English in one build, choosing the language from `System.uiLanguageCandidates`. The string tables can be JSON, read with `Scripts.evalJSONStorage` (the `json` plugin, which every build has).
- [ ] A hotkey (and a controller button) that switches the language while playing: the current message, the choices and the menus redraw in the other language, and the history keeps what was shown. Needs the item above; the framework has no language support yet.
- [ ] Line breaking with krkr_richtext's `StyledLayout` (`breakStrategy`, ruby, vertical text, per-character timing), in place of this fork's `needsToBeWrapped()` word wrap and its page-break edge cases.
- [ ] Menus built with Elements panels (`ElementsPanel`), which draw into a game layer and work with a controller, in place of the Win32 menu bar on every platform.
- [ ] A screenshot key that saves the screen as a PNG without a hitch: writing a 1920x1080 PNG takes about 90 ms, which shows, and `layerExSave`'s `startSaveLayerImage` writes it in the background (the plugin has to be linked before the game window is made, or the window lacks the method).
- [ ] A controls list: a screen that shows what every key, mouse button and controller button does (F1-F8, Shift+F11/F12 in debug mode, the D-pad and face buttons, R1/R2, START/BACK/L1), opened from Config and the menu above. It should read the bindings themselves (`AfterInit.tjs`'s `processKeys` hook and `padKeyMap`, `initialPadKeyMap` in `MainWindow.tjs`), so a game that changes them gets a correct list, and name the controller's buttons by the pad in use (✕/○ on a PlayStation pad, A/B elsewhere).
- [ ] Positional sound effects on World stages (`WaveSoundBuffer.use3D`, `SoundListener`).

## Needing more than scripts

These change the builds too: native code for every platform, including the web, Android and iOS engines in kagex-release's engine packages (the web build links its plugins into `krkrz.wasm`).

- [ ] **Live2D** (`krkrlive2d`): krkrz_dev has the plugin (`Live2DDevice`, `Live2DModel`, `Live2DPlayer`, `Live2DMatrix`), but builds it only with the Live2D Cubism SDK (the `CUBISM_SDK` environment variable), so the release workflow and `platforms.yml` would need the SDK, which Live2D distributes under its own license rather than as open source. Releasing a game with it can need Live2D's SDK release license, which the documentation should say. Then a World character whose poses and faces are motions and expressions, blinking by itself and lip-syncing to its voice as characters drawn from layers do (`WaveSoundBuffer.getSoundLevel`). `Live2DDevice` can take the engine's own OpenGL draw device (`OGLDrawDevice`), so it doesn't need `krkrgles`.
- [ ] **3D scenes and VRM characters** (`krkrthreepp`): threepp, a C++ port of three.js (scenes, cameras, lights, materials, glTF), and VRM avatars (VRoid and the like, 0.x and 1.0) with expressions, eye direction, VRMA animations, spring bones and MToon toon shading. It draws through the engine's `GLCompositor`, as krkreffekseer does, and the Windows, Linux and macOS packages already ship it. A `3d` flip type would render a scene into a layer, as `efk` plays effects; then World characters as VRM avatars, with faces as expressions, poses as VRMA animations and lip-sync through `WaveSoundBuffer.getSoundLevel`. The sample can't include a VRM model (no third-party art), so it would show a 3D scene built in script, and a game brings its own model. The plugin's presets include Android but not iOS or the web, and iOS may hit the same Xcode error as krkreffekseer.
- [ ] **Compiled scenarios, what's left** ([krkren/scnfile](https://github.com/krkren/scnfile), `doc/scn.txt`): CI for scnfile itself. Going back to a click in the middle of a message window shows that click's text alone (as a load does): the page's earlier lines could be redrawn from the history. A compiled script starts from an empty World; one that carries on from another script's screen needs the compiler to follow where it's reached from (the player's `depend` methods). A patch to compiled scripts needs the compile step too, and recompiling can move save points (the root `hash` lets the player notice): a save made before a patch should still land somewhere sensible.
- [ ] **M2's E-mote characters** (`emoteplayer`): E-mote is M2's 2D animation format (a character's `.psb`, made in the E-mote editor, moving its face, eyes, mouth, hair and body from one illustration), used by many Kirikiri games. The plugin that plays it is M2's own, from M2's SDK (an indie plan is free, commercial titles pay; check M2's current terms), and krkrz_dev's public build doesn't have it, so as with Live2D the builds would need the SDK, every platform's engine (the web, Android and iOS too) would need it linked, and releasing a game can need M2's license, which the documentation should say. Then World characters whose poses, faces and timelines are an E-mote model's, blinking and lip-syncing by its own variables (fed from `WaveSoundBuffer.getSoundLevel`, as the layered characters are), drawn through an AffineLayer source (krkrz_dev's TODO describes one, `AffineSourceMotion.tjs` with `SimpleEmotePlayer` and `SwitchEmotePlayer`, which this framework doesn't have). That TODO also notes that there each player makes its own `Motion.ResourceManager`, so a character's `.psb` (tens of MB) is read again on every action, and that sharing one per window crashed the plugin at unlink: use one cache per model, or find out what the plugin allows. The sample can't include M2's sample models (no third-party art), so it would need a model of its own made in the editor, or show the feature only when a game brings one.

## Looked at, not planned

- `layerExAreaAverage`: shrinks by area averaging, which `shrinkCopy` already does, in half the time and without the glitches `stretchCopyAA` left in text.
- `layerExLongExposure`: averages frames into one image, an authoring tool for rule images, which `tools/assets/make_rules.py` makes.
- `lineParser`: `[].load()` already reads a file line by line, and the framework parses with KAGParserEx and csvParser.
- `expat`: XML parsing; nothing in kagex reads XML, and only the desktop builds have it.
- `krkrgles` (Windows only): an OpenGL ES context through ANGLE, for engines without one. The SDL engine draws with OpenGL ES, and krkreffekseer, krkrthreepp and krkrlive2d use its context.
