# To do

Planned features, in four groups. The first three need only work in this repository (scripts, data and kagex-release): the plugins and engine features they use are already in krkrz_dev's default build and ship in the Linux package, and krkrz_dev itself isn't changed (`CLAUDE.md`). The fourth needs changes to the builds as well. The last section lists the plugins looked at and left out, and why.

## From krkrz_dev: plugins and engine features

- [ ] **Characters straight from PSD files** (`psdfile`): a character drawn from layers reads each pose's layers from psdlayer.tjs's text format, with a picture per layer (what `tools/assets/make_pip.py` writes for Pip). psdlayer.tjs can also read a `.psd` itself (`PSDInfo.loadPSD`, with psdfile's `PSD.getLayerData` rather than `psd://`, whose BMPs don't load outside Windows), so `StandPSDInfo` could take `<files>.psd` when there's no `.txt`, and artists could keep editing the PSD. Only the desktop builds have psdfile: either kagex-release writes the text format and pictures from the PSDs at build time (psdlayer.tjs's `saveImages` does it, but in the engine, with layerExSave and saveStruct), or the web, Android and iOS builds gain the plugin. kagex-release leaves `.psd` files out unless a script names them after `psd://`, so it would also keep the ones `charinit.csv` names. psdfile writes PSDs but can't make folders, so testing this needs a PSD writer of our own.
- [ ] **Mouths by vowel**: the engine's `WaveSoundBuffer.getVowel` estimates how much the voice sounds like a, i, u, e and o, so a face could have a mouth for each vowel instead of three openings. No plugin needed.

## Releasing

- [ ] **Compiled TJS** (`Scripts.compileStorage`, built into the engine): kagex-release compiles every `.tjs` in the package to bytecode, by running the engine headless with a compile script as its test run does, so a package carries no readable TJS and starts faster (the engine guide's anti-cracking topic recommends it). Bytecode runs through `Scripts.execStorage`/`evalStorage` like source, so `KAGLoadScript` doesn't change. It has to come after the media conversion, which rewrites file names in scripts as text. `@if` switches are decided at compile time (`DEBUG`, `KAGENV_OVERLAYER`, `OLDBOOKMARK` and others), so a package keeps the settings it was compiled with. Check that bytecode compiled on the host runs on every platform's engine, and whether `startup.tjs` can be bytecode. Strings stay readable (there's no obfuscator for TJS bytecode), so like Encrypted game files this keeps out casual reading, not a determined person.

## Needing more than scripts

These change the builds too: native code for every platform, including the web, Android and iOS engines in kagex-release's engine packages (the web build links its plugins into `krkrz.wasm`).

- [ ] **Live2D** (`krkrlive2d`): krkrz_dev has the plugin (`Live2DDevice`, `Live2DModel`, `Live2DPlayer`, `Live2DMatrix`), but builds it only with the Live2D Cubism SDK (the `CUBISM_SDK` environment variable), so the release workflow and `platforms.yml` would need the SDK, which Live2D distributes under its own license rather than as open source. Releasing a game with it can need Live2D's SDK release license, which the documentation should say. Then a World character whose poses and faces are motions and expressions, blinking by itself and lip-syncing to its voice as characters drawn from layers do (`WaveSoundBuffer.getSoundLevel`). `Live2DDevice` can take the engine's own OpenGL draw device (`OGLDrawDevice`), so it doesn't need `krkrgles`.
- [ ] **3D scenes and VRM characters** (`krkrthreepp`): threepp, a C++ port of three.js (scenes, cameras, lights, materials, glTF), and VRM avatars (VRoid and the like, 0.x and 1.0) with expressions, eye direction, VRMA animations, spring bones and MToon toon shading. It draws through the engine's `GLCompositor`, as krkreffekseer does, and the Windows, Linux and macOS packages already ship it. A `3d` flip type would render a scene into a layer, as `efk` plays effects; then World characters as VRM avatars, with faces as expressions, poses as VRMA animations and lip-sync through `WaveSoundBuffer.getSoundLevel`. The sample can't include a VRM model (no third-party art), so it would show a 3D scene built in script, and a game brings its own model. The plugin's presets include Android but not iOS or the web, and iOS may hit the same Xcode error as krkreffekseer.
- [ ] **Compiled scenarios** ([krkren/scnfile](https://github.com/krkren/scnfile), a plan so far): kagex-release compiles the `.ks` scripts in `!scnlist.txt` into encrypted `.scn` files that a plugin of our own (`SCNFile`) reads, and the scene player in `KAGEnvPlayer.tjs` (`[scenestart]`, the World's `playerExecMode`) plays them. That gives scripts out of plain view, jumping to any line, rollback, read tracking per line and dialogue search, all of which the player already has. Its first milestone needs no plugin: the compiler writes `.scn.json`, which the player reads with `Scripts.evalJSONStorage` (`json`, in every build), so it's script work here. The `.scn` files are encrypted with the same key as the archive (below). A patch to compiled scripts needs the compile step too, and recompiling can move save points (the root `hash` lets the player notice).
- [ ] **Encrypted game files** (the scnfile plugin and key above, not a scheme of its own): kagex-release encrypts every file in `data.xp3`, and the plugin decrypts each one as the engine reads it, through the engine's XP3 extraction filter (`TVPSetXP3ArchiveExtractionFilter`; the engine at `21d20e9` still calls it for every read). On Windows, Linux and macOS the plugin ships as a `.tpm`, which the engine loads before `startup.tjs`; on the web, Android and iOS it's linked in and sets the filter from its startup hook. krkrz_dev has nothing for this: krkrz_tools' xp3 writer only sets the "protect" flag, a notice to extraction tools, and doesn't read or write the Kirikiri 2 Releaser's `xp3enc.dll` encryption either. The cipher is a standard one, XChaCha20 (Monocypher), keyed per file. The filter decrypts reads at any offset, which a stream cipher can seek to, but which leaves no place to check a whole-file tag, so tampering is caught by signing (below) rather than by the cipher. Brute force isn't the threat (a 256-bit key can't be guessed); taking the key out of the game is, since the game has to carry it. So the work goes into the key. It's per game: kagex-release writes each game's key into the plugin of that game's engines (prebuilt engines can't have it compiled in), before signing (macOS, iOS, Android) and before the web build's id, so breaking one kagex game doesn't open the others. It's never one block: the plugin assembles it at run time from pieces scattered through the binary. Each file gets its own key, derived from the game key and the file's hash (the filter's `FileHash`), so a key lifted from memory for one file doesn't open the rest. And none of it is in TJS. The extraction filter only sees file contents, so the archive's file list stays readable; hiding it too means an archive of our own with an encrypted index, which the plugin serves as a storage medium (as minizip serves `zip://`) and a minimal plain `startup.tjs` mounts. Not planned: a cxdec-style routine generated per game. It adds obscurity, not strength (cxdec is undone by recovering each game's routine), the plugin's source is public anyway, and generated code per game would mean compiling a plugin for every game on every platform. The key still ships with the game, so a determined person gets in; this makes each game take real work.
- [x] **Signed game files** (`sigcheck`, since 0.9.0): kagex-release signs the game archive (or the executable it's bound into), the engine and its plugins, the per-folder/part archives and each patch zip with the developer's RSA key (RSA-PSS/SHA-256, `<file>.sig`; the private key is kept out of the repository and is never stored in `release.json`). At start the game (`template/system/SignatureCheck.tjs`) checks them with `Window.checkSignature` and the public key written into `data.xp3`, and starts `first.ks` only when they all pass; otherwise it names the file and quits. `checkSignature` is a method of the game window, so no separate window is needed; the check is asynchronous, so start-up is gated on its completion and patches/extra archives mount only after the framework and `Config` load (they can change assets, not the framework). A self-test (a decoy with a mismatching signature) catches a stubbed plugin, and the build refuses REPL/startup options and debug mode. The SDL engine has none of the old Kirikiri executable markers, so sigcheck hashes each file whole; the engine files to check are listed in a signed `<exe>.sigfiles` beside the executable. The web, Android and iOS builds have no plugin, so they skip the check (signed by the platform / served from the developer's site). Done in this repository and kagex-release alone (the plugin and `krt::sig` were already in krkrz_dev); the open items are the plugin's 32-bit size limit and its repeated reads (`UPSTREAM.md`), worked around here by splitting archives under 2 GB. Compiled scripts and an encrypted archive (above) would make the in-archive check much harder to remove.

## Looked at, not planned

- `layerExAreaAverage`: shrinks by area averaging, which `shrinkCopy` already does, in half the time and without the glitches `stretchCopyAA` left in text.
- `layerExLongExposure`: averages frames into one image, an authoring tool for rule images, which `tools/assets/make_rules.py` makes.
- `lineParser`: `[].load()` already reads a file line by line, and the framework parses with KAGParserEx and csvParser.
- `expat`: XML parsing; nothing in kagex reads XML, and only the desktop builds have it.
- `krkrgles` (Windows only): an OpenGL ES context through ANGLE, for engines without one. The SDL engine draws with OpenGL ES, and krkreffekseer, krkrthreepp and krkrlive2d use its context.
