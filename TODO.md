# To do

Planned features and fixes. The first section's need changes to the builds as well as work in this repository, and the second's wait on the engine: krkrz_dev itself isn't changed (`CLAUDE.md`), and what it and its plugins can't do yet is in `UPSTREAM.md`. Many entries came from moving a commercial game made with Wamsoft's framework to KAGEX's engines; they describe what such games do, for KAGEX to write again from scratch with its own names, formats and assets, taking none of that game's code, data or art. The last section lists the plugins and features looked at and left out, and why.

## Needing more than scripts

These change the builds too: native code for every platform, including the web, Android and iOS engines in kagex-release's engine packages (the web build links its plugins into `krkrz.wasm`).

- [ ] **Voice effects** (a plugin of KAGEX's own): an echo on memories and inner voices, a thin voice on the phone, a muffled one through a door, as commercial games have them. A writer sets an effect with a World tag, for one character or for all until it's cleared, and each effect's settings are in a small text file; the effect is kept in save data, so compiled scenes, saves and going back carry it. KAGEX has no sound filters besides the phase vocoder for voice speed, though `VoiceTrack` (`KAGEnvCharacter.tjs`) already keeps a `filters` chain, and 0.12.0's positional sound (`WaveSoundBuffer.use3D`, `KAGEnvSE.tjs`) pans and sets distance but doesn't filter, so a phone or a door still needs this. The plugin would be engine wave filters (`iTVPBasicWaveFilter` over a `tTVPSampleAndLabelSource`, float output, settings changed on the decoding thread): a delay, biquad and Butterworth filters, perhaps a reverb, with DSPFilters (MIT) for the filter designs, built into every engine as scnfile is (static on the web, Android and iOS); without it, voices play unchanged. The sample gets a demo line: Pip on the phone. The `WaveFilters` plugin written for a port already has a delay and DSP filters, but its delay was rebuilt from the disassembly of a Wamsoft DLL and its class names follow Wamsoft's, so shipping it as it is is the maintainer's decision; otherwise KAGEX writes its own, with its own names and API.
- [ ] **Glitch transitions** (a plugin of KAGEX's own): digital glitches (rows of noise, shifted blocks, split colours) as a transition in the story, and when menus open and close, pages turn or a game loads, as some of Wamsoft's games do; single glitched frames also give a "broken screen" inside a scene. KAGEX has extrans's and extNagano's transitions, with a crossfade when a plugin is missing (`KAGTransitionMethod`), which already covers a build without this one, and its system screens have no set transition. A transition plugin with its own glitch algorithm and parameters, built into every engine as scnfile is; a framework setting for the transitions its screens open, close and turn pages with; and a demo step in the sample's `transition.ks`. The `GlitchEffect` plugin written for a port reproduces a Wamsoft DLL from its disassembly, down to its random numbers, so it's better kept for that port, with a new design written for KAGEX: that's the maintainer's decision.
- [ ] **Opening web pages, folders and programs on every platform** (`ShellExecute`): a "Visit the website" menu item, a button that opens the screenshot folder, a link in the credits, and for developers a helper program whose output they read. The SDL engine has the code (`app.cpp`, through `SDL_OpenURL`) but binds no `System.shellExecute` for scripts, so a call throws, and KAGEX's own Help > Contents calls it (`onHelpIndexMenuItemClick`, `template/system/MainWindow.tjs`); krkrz_dev's `shellExecute` and `process` plugins are Windows-only and not in the engine packages. Either the engine binds it (a krkrz_dev change, for `UPSTREAM.md`), or KAGEX ships the `ShellExecute` plugin written for a port: krkrz_dev's plugin rebuilt for every platform from the public APIs (ShellExecuteEx and CreateProcess on Windows, posix_spawn with `open` or `xdg-open` on macOS and Linux, `SDL_OpenURL` on Android, iOS and the web, programs polled from the continuous event rather than by threads), tested on Windows, Linux and Android, and free to ship as it is; on the web, Android and iOS it has to be in the engine package (`tools/release/README.md`, "Your own plugins"). The sample shows it with a "website" item in the title or system menu, and the in-game manual, the screenshot folder and the debug helpers below use it.
- [ ] **Text to speech with the system's voices** (`SpeechSynth`): for players who can't or don't want to read, each line read aloud by one of the system's voices and played like a voice line (auto mode waits for it, and it follows the voice volume), with the voice, its speed and pitch chosen per kind of speaker, and a pronunciation dictionary. Since 0.12.0 each message goes to the system's screen reader (`KAGA11y`), which speaks with the reader's own voice and settings, not on the game's voice channel, and isn't there in the browser, Android and iOS builds. The `SpeechSynth` plugin written for a port speaks into a WAV file (SAPI on Windows, `say` on macOS, espeak-ng on Linux, Android's `TextToSpeech.synthesizeToFile` through JNI) from public APIs, so it can go to KAGEX as it is, with a small framework module that speaks each page into a file, plays it on a voice buffer and offers the voices of the language being played. iOS could do the same with `AVSpeechSynthesizer.write` (iOS 13), built on a Mac; the browser's `speechSynthesis` only speaks aloud, so there the module would use it directly, without the voice channel's volume and wait. Android needs a manifest query for the speech service, which kagex-release's Android builds have had since 0.17.0 (`platforms.android.ttsQuery`; the sample's own APK, built from the kit in `platforms.yml`, still lacks it). A Config switch picks the game's speech, and turns `kag.a11yReadText` off while it's on, so a line isn't read twice.

## Needing krkrz_dev

These wait on the engine, which kagex doesn't change (`CLAUDE.md`): each gets an `UPSTREAM.md` entry (where, what it costs, the fix) once it's confirmed at the engine `ENGINE_SHA` pins, and the framework works around it meanwhile where it can. The first two are features; the rest were found moving a commercial game to KAGEX's engines at `21d20e9`, and a few of them need only a note in `doc/`.

- [ ] **The game's own mouse cursors, and a jump to the default button**: the game can have its own cursor, a picture matching its art, and another over buttons, with a setting to go back to the system's; and when a Yes/No prompt opens, the cursor can jump to its default button (Yes or No, as the player chooses) or stay. KAG's `[cursor default= pointed= click=]` and `cursorPointed = crHandPoint` are there, but the SDL engine always shows the system arrow, not even the hand over buttons: `TVPGetCursor` returns 0, "not supported yet" (krkrz_dev `generic/visual/WindowImpl.cpp`), and `SetMouseCursor` does nothing (`generic/environ/WindowForm.h`). The engine would map the `cr*` cursors to `SDL_CreateSystemCursor` and load `.cur` or PNG cursors with `SDL_CreateColorCursor`; until then the framework can draw the cursor as a top layer that follows the mouse, with the system's hidden (`mouseCursorState`), switched by a Config setting. The jump needs no engine change: it's commented out in `template/system/YesNoDialog.tjs` (`-curmove`), and the engine can move the cursor (`SDL3WindowForm::SetCursorPos` warps it), so it comes back behind a `scflags` setting (Yes, No or off). Desktops and the browser; phones have no cursor.
- [ ] **Mute or pause in the background**: when the window loses focus the game keeps playing, mutes, or pauses (text, animation and auto mode wait, the sound is muted, and the screen dims with a "paused" mark until the player comes back); a playing movie isn't stopped. The SDL engine gives scripts no `onActivate` or `onDeactivate`, for the window or the application: nothing in krkrz_dev's `sdl3/` posts `AM_PAUSE`/`AM_RESUME` or calls `TVPPostApplicationActivateEvent`, and `SDL_EVENT_WILL_ENTER_BACKGROUND` only stops the drawing (`sdl3/environ/main.cpp`); `WaveSoundBuffer.globalFocusMode` (never, on minimize, on deactivate) depends on the same state. The engine would forward SDL's focus events (`SDL_EVENT_WINDOW_FOCUS_LOST` and `SDL_EVENT_WINDOW_FOCUS_GAINED`) and the move into the background to the activate events. Then a framework setting in `scflags`: mute through `WaveSoundBuffer.globalVolume`, or pause with `System.eventDisabled` (stopping auto mode, voices and the BGM) and dim the screen with an ordinary layer on top (the SDL engine has no `setOverlayBitmap`), and a Config row in the sample, "In the background: keep playing, mute or pause". The same events let the continue save (0.16.0) be written as a phone puts the game away. Desktops and the browser (switching tabs); phones stop apps in the background already.
- [ ] **Android: plugins opened at run time free into the wrong allocator**: `libkrkrz.so` defines and exports its own `operator new` and `delete`, and `libc++_shared.so`, loaded with it, uses them for what it allocates itself (a `std::string`'s buffer), but a plugin opened later with `dlopen` resolves its own `delete` to the C++ library's plain one, so the first `std::string` a plugin frees stops the game ("Scudo ERROR: corrupted chunk header", `SIGABRT`). A plugin can take the engine's `new` and `delete` itself (the `ShellExecute`, `SpeechSynth` and `WaveFilters` plugins each carry an `AndroidAllocator.cpp` for it). KAGEX's own Android builds link their plugins into the engine, which this doesn't touch; it's for a plugin loaded at run time (the APK entry below). The fix upstream: don't replace them on Android, or have the plugin loader hand them to plugins; until then, a note for plugin authors.
- [ ] **`user://` storage drops saves without an error**: the media splits `user://<domain>/<path>` at the first `/`, so a name with a doubled slash (a folder ending in `/`, then `/`, then a file, which `System.dataPath`, ending in `/`, invites) hands SDL's storage an absolute path, which it refuses; a write is held in memory and written when the stream closes, where a failure is only logged, so the save "succeeds" and the next read throws "Cannot open storage". That's the save folder on Android, iOS and the web. The fix: collapse repeated slashes in `SDLStorageMedia`, and let a failed write reach the script (or at least the log in a release build). The framework's own save names have had one slash since 0.16.0 (`kag.saveDataFile`); a game's own names may still double it.
- [ ] **The file pool deadlocks when it fills**: the allocator calls the storage cache's pressure handler while holding its own lock, and the handler frees into the same pool. A game with about 240 MB of embedded fonts filled the default 256 MB pool at start-up and hung; `filepoolsize=none` in the game's `krkrz.cf` avoids it (on Android, iOS and the web too since kagex-release writes it into their `config.cf`).
- [ ] **`Storages.copyFile` throws for a file that isn't there**: fstat's `copyFile`, which Wamsoft's and older KAG scripts were written against, returned false, so a game's rotating saves that copy an empty slot fail on the first quick save (the framework's own, since 0.16.0, go round without copying). The fix: return false, or say it in `doc/` (the porting notes).
- [ ] **A multi-line text field for Elements screens**: ElementsDialog's `input_box` is one line, so a save comment, a note or anything longer needs one field per line.
- [ ] **Notes for plugin authors**: a global of an engine type (`ttstr`) at namespace scope is built when the library loads, before `V2Link` hands over the engine's functions, and the engine reports "A dynamic link library (DLL) initialization routine failed"; and a plugin opened at run time on Android needs the allocator fix above. A note in `tools/release/README.md`'s "Your own plugins", which a game's own plugins (0.13.0) make the place for; it could also say for every plugin what `tools/live2d/README.md` says for the Live2D one, that a Linux plugin needs the glibc it was built against (one built with GCC 13 on glibc 2.38 asked for `__isoc23_sscanf`), so build it in the Steam Runtime as `--steamrt` does.
- [ ] **The web engine can't fetch a file name with `%`, `#` or `?`**: `tTVPHttpStorageMedia::ToUrl` and `ResolveUrl` (`sdl3/base/HttpStorageMedia.cpp`) put the name into the URL as it is, and krkrz_web's prefetch (`web/pre.js`) does the same. So `window@base%base.png` asks for `%ba` and 404s, and the missing picture stops the engine (`RuntimeError: null function` in `TVPLoadGraphic`). Games made with Wamsoft's framework name their UI pieces that way (79 files in one commercial game). The fix, tested in a browser: encode the three in both places alike, since the prefetch's URLs are also its cache keys. A fetch wrapper in the page works around it on an engine without the fix, but would encode the names twice on one with it.

## Fixes in kagex-release

Found building a game for every platform with kagex-release, and still there at 0.16.0.

- [ ] **A game's own plugins in the Android APK, without an engine package of its own**: since 0.13.0 a game's own plugins in `plugins/windows/`, `plugins/linux/` and `plugins/macos/` go into the desktop packages, and on the web, Android and iOS a plugin of the game's own means an engine package built with it (`tools/release/README.md`, "Your own plugins"), so `check` warns about a `plugins/android` folder. But the Android engine also loads a plugin it doesn't have built in as `lib<name>.so` from the app's libraries, so kagex-release could copy `plugins/android/<abi>/*.so` into the Gradle project's `app/src/main/jniLibs/<abi>/` and let a game add a plugin without building an engine (such a plugin must take the engine's `new` and `delete`: the allocator entry above). iOS and the web can't do this: they load no plugins at run time.

## Saving and moving through the story

- [ ] **Save before running out of memory**: when memory runs low, the game writes the continue save (0.16.0's place to carry on from) and offers to restart, instead of the engine failing on a full pool. The engine tells scripts nothing about memory: it would post an event when an allocation from one of its pools (`-filepoolsize`, `-krkrzpoolsize`) fails or nears its limit, or when the system warns (`SDL_EVENT_LOW_MEMORY` on Android and iOS). Then `kag.saveContinue(true)` and a Yes/No prompt in the framework. Every platform.
- [ ] **Saves that survive script patches, and a report of what changed**: after a patch, players' saves still resume at the line they were made at. A save keeps its scene's hash and save point, and when the hash differs it starts at the top of its scene (`KAGEnvPlayer.onRestore`, `doc/scn.txt`); the hash covers the script's MD5, the macros, `envinit.tjs` and `charinit.csv` (`SceneParser.sourceKey`), so a patch that only changes `envinit.tjs` sends every save back to the top of its scene. kagex-release and `-scncompile` would write each build's save points beside its file list (`<exe>-<version>-points.json`: per scene, each point's text number and a hash of that text and its speaker), and a build with `output.patchFrom` lines the old texts up with the new by those hashes (as a diff does, since text numbers shift when lines are added) and writes a map from the old points to the new into each `.scn`, for the points that moved. `onRestore` then maps the save's point instead of resetting it, and keeps it when no point moved. For the developer, a `scndiff` tool beside `scn2ks` in scnfile reads the same JSON and PSB and prints the texts that changed, and those whose World state on screen differs (each shown object's image, filters, final properties and stacking); CI could run it on the sample. Data only, so every platform.

## The message window and text

- [ ] **A menu language of its own, and two languages at once**: since 0.10.0 the story's language switches while playing, translations are compiled into each `.scn`, and interface strings and stand-in files come from `data/lang/<code>/`, but the story and the interface share one language, and only one is shown at a time. What's left: a menu language apart from the story's (a second setting, with the story's `data/lang` folder taken off the search path for interface files); a second language under the first, for language learners or two players, which the compiled scenes already carry, so it's the message window's drawing, a font scaled to fit two, a key that swaps them, and perhaps both in the backlog; and checks for translators as the compiler matches texts (narration given a name, a speaker whose name differs, a count that doesn't match), with a per-language report from `-scncompile` of the texts still in the script's language. Chinese needs SC and TC fonts, too large for the web build's download, so they'd ship as language packs (`KAGMountPatchZip`).

## Screens, menus and controls

- [ ] **A frame-rate limit, and full screen filled by a percentage**: since 0.19.0 Config offers the window's sizes that fit the screen, how full screen fills a screen of another shape (black bars, fill and cut, stretch: `Window.setViewport`'s modes), smooth scaling (`-smoothzoom`) and vsync (`Display.tjs`). What's left: a frame-rate limit (`-contfreq` is read only by the Windows engine: a krkrz_dev change for `UPSTREAM.md`), a fit between bars and fill by a percentage (`KAGWindow.onResize`'s `-fszoom middle` and `-mzpercent` apply only to the Windows engine's free-resize mode; on the SDL engine it would be `setViewport("custom", zoom, ...)` with the zoom worked out), the Display menu's items for the sizes (`Menus.tjs`), and the settings read before the window is made on Android, iOS and the web, which read only `config.cf`.
- [ ] **Screenshots: a folder, copying and opening it**: since 0.19.0 a screenshot can leave out the message windows, be PNG or JPEG, carry a watermark and a name pattern, and a scene can turn them off (`[screenshot]`, kept in saves; `Display.tjs`, `MainWindow.tjs`), and since 0.20.0 its notice shows the picture and the sample's quick menu has a button for it. What's left: a choice of folder (the save folder or the pictures folder, `System.personalPath`: the SDL engine has no file dialog), overwrite or not, and opening the folder (needs `System.shellExecute`, above); copying the picture fails, since the SDL clipboard takes text only and setting a bitmap returns false (krkrz_dev `sdl3/utils/ClipboardImpl.cpp`), a krkrz_dev change for `UPSTREAM.md`. A phone's photo gallery would need native code.
- [ ] **Advanced settings, and a restart that comes back to the same place**: settings for when something goes wrong, out of the casual player's way: an Advanced menu that shows only after a Help item reveals it, with low-memory mode, image cache sizes, drawing threads, the frame-rate limit, controller off and movie quality; a setting that needs a restart says so and offers to restart now, and the game saves its place first and comes back to it. Engine options come only from the command line or the config file, and nothing restarts the game; the SDL engine reads `-memusage`, `-drawthread`, `-joypad`, `-renderer` and `-gclim` at start, and a few again when `System.setArgument` changes them (`-smoothzoom`, `-paddelay`, `-padinterval`); and `template/system/standview.tjs` calls a `changeUserConf` that KAGEX doesn't define. Framework: a small table of engine options (name, values, label, live or restart) in an Advanced menu of the 0.12.0 menu bar, kept in `scflags` and in `<exe>.cfu` on desktops, with `changeUserConf` defined (which also mends `standview.tjs`). Restart: save a resume point (the continue slot above) and start again, which needs a relaunch in the engine (an `UPSTREAM.md` entry) or `System.shellExecute` on `System.exeName`; on Android, iOS and the web, say "from the next start" instead. The settings on every platform; relaunching on desktops.

## The World and staging

- [ ] **Android sometimes freezes in the first demo's rotation**: reported on Android: the game now and then stops responding in the KAGEX Extended Layer demo (`layer.ks`, the demo menu's first choice) at its rotation section, `*label2|Rotation` (`[layopt layer=0 rotate=30]`, then the rotation origin moved with `afx`/`afy`); the later angle and spinning sections (`*label9`, `LayerToRotateModule`; `*label10`, `LayerNormalRotateModule`; `*label12`) rotate the same layer, so the report may mean one of those. `platforms.yml`'s Android smoke test plays `layer.ks` to the end on the emulator with a clicking `Timer` and hasn't hung there, so it's intermittent or needs a player's pace. It isn't the sound threads' deadlock (`UPSTREAM.md` 44): `layer.ks` plays nothing before its movie section, and the sample's music has no labels since 0.18.0. The hunt for it (`smoketest.py --hunt`, `platforms.yml`'s `hunt` input: `layer.ks` from `*label2` to `*label13` over and over at a player's changing pace, with the game's thread stacks taken through `debuggerd` if it stops answering) ran it 50 times on the emulator without a hang (run 42168118362), so it may need a real phone's GPU or timing. Next: the same hunt on a phone (`--target android` with the debug APK over adb), or the reporter's logcat (`SDL/APP`) and `debuggerd -b` while it's frozen, then decide whether it's the framework (the affine layer's drawing, `AffineLayer.tjs`; the actions) or the engine (then an `UPSTREAM.md` entry and a workaround here).
- [ ] **Smaller packages for flat CG variations**: a variation drawn as a whole picture is stored whole. Layered CGs make their variations from one file since 0.26.0 (`CGVariations.tjs`, `cgvariations.txt`). Tool: kagex-release compares each flat variation with its base and stores the rectangle that differs and its offset, which the framework puts back together when loading (the web build, which downloads the whole package, gains most).
- [ ] **Ripples that bend the picture**: since 0.18.0 kagex draws multiripple itself (`ScriptTransitions.tjs`), and its `maxdrift` makes the wave rings brighter; the plugin meant it as how far the waves bend the picture under them, which takes a displacement per pixel each frame: too slow in a script at 1920x1080, so it needs a shader (`GLCompositor`) or the plugin fixed (`UPSTREAM.md` 42).

## Sound, voices and movies

- [ ] **kagex-release makes movies' smaller versions**: since 0.17.0 `[movie]` plays `<name>_sd` on the web and phones, or when the player picks Smaller in Config (`KAGMovieFile`, `template/system/Movies.tjs`), but the developer makes those files by hand. kagex-release could make them once it converts video (the porting kit below): a half-size `.webm` at a lower bitrate for every movie in `data/video`, cached like the other media, and a Media setting to turn it off. ## Tools for developers

- [ ] **A playthrough tester and debug helpers for your own game**: run every route of a game unattended in skip mode, picking a given choice at each menu, and get the first script error with where it happened, or a "stuck" after too long in one place; one-line helpers that log every tag with its timing, the visible layer tree or the World's definitions; and a Debug menu for writers: restart the current script from its top (Reload Scenario reloads it where the player is), go back 100 lines or to a line number, open the script at the current line in an editor, pick an earlier point to go back to, view and change the game's flags from a commented list, copy the current voice's file name or a description of the scene, and write a bug report. `tools/smoketest.py` plays the sample's own steps through the REPL file channel and only starts the template, and nothing points at a developer's own routes; the sample's Debug menu has Load and Reload Scenario, the console, Controller, System Reset, the debug levels and window, Return to Previous Trace, the KAGEX log and voice speed. A `tools/playtest.py` on smoketest.py's REPL channel and engine handling (headless on Linux with the offscreen driver, in a window on Windows), with choices given as a list (`--choices 0,1,0`) or every branch in turn, its own `-datapath` and log per run, and a way past the single-instance lock for parallel runs (`createAppLock` is keyed by the executable's path, `template/system/Initialize.tjs`); framework helpers loaded only in debug mode (a route runner over the compiled scenes' choices, a tag trace, a layer dump, a World dump, and an `-allseen` switch that's never saved); and the Debug-menu items, in debug mode only: restart and go to a line (`player.seek` by text number in compiled scenes, the line of an automatic label in scripts KAG plays), open in an editor (an `-editor=` command with the file and line, which needs `System.shellExecute`, above), a flags screen from a list file (name, comment, value) as an Elements screen, copying through `Clipboard.asText` (which works on SDL), and a bug report (position, flags, the log's last lines and a screenshot in one folder). Desktops and CI; the scene data it plays is what every platform ships.
- [ ] **A porting kit for older Kirikiri games**: move an existing Windows Kirikiri or KAGEX game to KAGEX's engines without rewriting it. The README's "Not available on the SDL3 build" lists the missing Windows plugins; 0.12.0's menu bar draws a game's own `KAGWindow_createMenus` menu, which covers menu.dll for games on KAGEX's framework; a movie named without its extension finds its `.webm`; and kagex-release converts sounds and images but not video. A `doc/porting.txt`: the engine differences, the rules for stand-ins (overrides of native class methods installed before any instance exists; a stand-in takes every option its callers pass), and the notes for Android and iOS (the engine entries above: the fixed 1920x1080 surface, full screen from the start, the save folder's slashes, `Storages.copyFile`), with one more: the Android engine links its built-in plugins before any script runs (`TVPLoadStaticPluigins`), so a game that checks for a plugin's method to decide whether to link it skips the whole block, settings included (a voice script never set `WaveSoundBuffer.enableGetSample`, and every voiced line with a moving mouth stopped with 'Member "enableGetSample" does not exist'). KAGEX's own scripts already guard each link that way on purpose (`KAGLinkPlugin`, `CLAUDE.md`); the note is for games brought from elsewhere. An optional template helper that sends `Plugins.link` through a table, mapping each plugin to a KAGEX plugin (renamed or not), a script stand-in, something built into the engine, or "missing", so the game's own fallback runs, with stubs for Windows-only calls; and the stand-ins worth having for any old game, written from what scripts ask of each API: win32dialog.dll's dialog templates drawn as Elements panels (many games' config and save dialogs are built on it; the largest piece), the original engine's data packs (`Scripts.saveDataPack`, `loadDataPack`, `Storages.saveOctet`) and getLangName.dll's system language name. Stand-ins written for a port copy no plugin code and can be a start, but one for textrender.dll would follow a Wamsoft DLL's interface, so KAGEX would want its own design there. An optional video step in kagex-release (VP9 and Opus through ffmpeg, with a quality check), which could also make the small movie versions above, and the game's icon taken from its old `.exe` as `identity.icon`. The tools run on desktops; their output works on every platform.
- [ ] **kagex-release measures loudness**: since 0.18.0 `loudness.csv` evens out levels by kind and by file, written by hand. kagex-release, which turns WAV and FLAC into Opus, could measure each sound's loudness as it converts it (EBU R128, for example with libebur128, MIT), write the per-file table to bring each folder to a target, and list the files far from it; WAV files kept as WAV get no gain, which it should say.

## Looked at, not planned

- M2's E-mote characters (`emoteplayer`): E-mote's player comes only from M2, through an application and a contract for its SDK (even the plan for small developers), and no player for SDL3 Kirikiri Z is public: Wamsoft's krkrz plugin is private, and M2's Kirikiri one is a closed DirectX DLL for Kirikiri 2. A player of our own, written from the reverse-engineered format, would get around M2's licence (FreeMote, the work on that format, is noncommercial only). Live2D covers the same ground (`doc/world.txt`, "Live2D Characters"; the `l2d` flip). If M2's SDK is ever in hand, the plan is Live2D's: a krkrz plugin around its player library drawing through `GLCompositor`, World characters on `KAGEnvCharacterEyeLip.tjs`, an `emote` flip type, a stand-in for the smoke test, and the SDK in a private repository for CI.
- `layerExAreaAverage`: shrinks by area averaging, which `shrinkCopy` already does, in half the time and without the glitches `stretchCopyAA` left in text.
- `layerExLongExposure`: averages frames into one image, an authoring tool for rule images, which `tools/assets/make_rules.py` makes.
- `lineParser`: `[].load()` already reads a file line by line, and the framework parses with KAGParserEx and csvParser.
- `expat`: XML parsing; nothing in kagex reads XML, and only the desktop builds have it.
- krkr_richtext's per-character timing (`StyledLayout`'s `<delay>`, `<wait>` and `calcShowCount`): it times a text laid out whole, while KAG's conductor gives the message window a character at a time with its own waits, skipping and auto mode, so KAG keeps timing the characters (krkr_richtext lays out and draws each line of them: `useStyledLayout`).
- `krkrgles` (Windows only): an OpenGL ES context through ANGLE, for engines without one. The SDL engine draws with OpenGL ES, and krkreffekseer, krkrthreepp and krkrlive2d use its context.
- BISHAMON particles and Direct3D: another company's particle middleware, on Windows' Direct3D only; KAGEX has Effekseer for particles, and krkrthreepp's 3D on every engine since 0.14.0.
- Windows-only features of Wamsoft's games: stay on top, the taskbar preview, the panic key, the Windows display methods, full screen across several monitors, the mouse wheel through DirectInput, the movie display modes, the bitmap allocator, Win32 dialogs and launcher programs. They're tied to Windows, and KAGEX's engines run on seven platforms.
- Comments typed on saves: Wamsoft's games take them in a Win32 dialog, and Elements screens have no multi-line text field for them (above).
